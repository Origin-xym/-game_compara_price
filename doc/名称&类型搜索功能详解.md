## 一、一句话链路

输入框（防抖 300ms）→ `filters.keyword` → `GET /api/games?keyword=` → 后端把关键词**归一化**成 `keywordNorm`，并**预先解析成“可能命中的类型 id”** → 一条 SQL 用多路 OR（中文名 / 英文名 / 属于命中类型，类型同时查 `game_type_id` 与 `game_type_rel`）匹配 → 返回列表 → 卡片按名称高亮命中片段。

## 二、接口

| 接口 | 是否参与搜索 | 说明 |
| --- | --- | --- |
| `GET /api/games?keyword=xxx` | ✅ 唯一入口 | 关键词走 query 参数，与 typeIds/platformIds/价格区间共用同一个 DTO |
| `GET /api/game-types` | 间接 | 只用于筛选栏的类型下拉；**搜索命中类型不走它**，而是后端查 `game_type` + `game_type_rel` |

按当前数据（22 款游戏 / 5 个类型）实测口径：

| 输入 | 结果 |
| --- | --- |
| `赛博` | 1 条 · 赛博朋克2077 |
| `赛博 朋克` | 1 条（空格被容忍） |
| `角色扮演` | 3 条（**类型名命中**，把整类游戏返回） |
| `rpg` | 3 条（**类型 code 命中**，大小写不敏感） |
| `cyberpunk` / `ELDEN` | 各 1 条（英文名命中） |
| `只狼` | 1 条（中名命中） |
| `不是游戏` | 0 条 |

> 2026-11-27 核对：类型已从 3 个扩到 5 个（动作 / 角色扮演 / 策略 / 冒险 / 开放世界），且游戏可挂多个标签，所以"类型命中=整类返回"现在要按 `game_type_rel` 一并算。

## 四、一次搜索的工作流

1. 用户键入 → `SearchBox` 的 `inner` 变 → 立刻 `emit('update:modelValue')`（父 `filters.keyword` 同步，用于条件标签显示）→ **300ms 后才** `emit('search')`；
2. `handleSearch(kw)`：写 `activeKeyword`（高亮用）→ `applyConditions()` 把 `page=1` → `fetchList()`；
3. `buildParams()`：`keyword` 有值才带上，否则 `undefined`（axios 会丢弃空参数）；
4. 后端 `@ModelAttribute` 绑定 + `@Valid` 校验长度；
5. `prepareKeyword`：
   - 空 → `keywordNorm=null`、`keywordTypeIds=null`，SQL 里 `<if>` 整段跳过（等价于不过滤）；
   - 非空 → 去首尾 + **去所有空白** + 小写 → `keywordNorm`；再用原始关键词查 `game_type`（名称 like / code 大写相等）→ `keywordTypeIds`；
6. `selectAppPage` 执行：`status=1` AND `( name LIKE %kw% OR name_en LIKE %kw% [OR game_type_id IN (...) ] )`，同时叠加类型/平台/价格/折扣条件，MyBatis-Plus 分页插件补 `LIMIT` 并单独 count；
7. 批量补类型名与当前价（`loadTypeNames` / `loadCurrentPrices`），组装 `GameListItemVO`；
8. 前端拿到 `list/total` 渲染卡片，`GameCard` 用 `activeKeyword` 按**同一条规则**（`\s*` 连接）切段高亮。

## 五、这里的知识点

- **双向绑定手写实现**：`v-model` = `:modelValue` + `@update:modelValue`；组件内用 `inner` 副本 + 两个 `watch` 防回环（父改 → 子改；子改 → 父改，但相等就不写）。
- **防抖（debounce）**：`clearTimeout + setTimeout`，只在停顿 300ms 后请求；比 `throttle` 更适合“输入即搜”。`clear` 按钮也复用同一条 watch 链路，所以清空会立即搜一次空关键词。
- **“草稿词” vs “生效词”**：`filters.keyword`（输入值）与 `activeKeyword`（已提交值）分离，避免输入到一半就高亮错位。
- **归一化在两侧都要做**：Java 侧 `replaceAll("\\s+","")` + `toLowerCase`，SQL 侧 `REPLACE(LOWER(name),' ','')`，两边必须同规则，否则“搜得到但高亮不到”。
- **类型搜索的两种命中**：类型**名称**（`like`）与类型**编码**（`UPPER(code)=UPPER(kw)`），所以 `rpg` 和 `角色扮演` 等价；命中后先把类型解析成 id，再在 SQL 里用 `game_type_id IN (...) OR EXISTS(game_type_rel ...)` 双路匹配 —— 因为现在一款游戏可以挂多个标签，只查 `game_type_id` 会漏掉"副标签"。
- **高亮只覆盖名称**：`GameCard` 的 `.hit` 只作用于 `nameParts`（名称分段）；类型标签是 `el-tag` 纯文本，所以"搜类型名命中"时类型标签不会变红。`typeParts` 计算属性仍在（历史遗留），当前模板未使用。
- **大小写不敏感**：`LOWER()` + `keywordNorm` 小写；中文无影响，英文有效（`ELDEN` 命中 `ELDEN RING`）。
- **LIKE 无法走索引**：`%kw%` 前后都有通配，B+Tree 索引失效。现在 6 条游戏无所谓；上千条后要换全文索引（MySQL `FULLTEXT` + `ngram` 分词）或上 Elasticsearch。
- **动态 SQL 的条件缺省**：`<if>` 包裹整段 OR，避免出现 `AND ()` 或空 `IN` 的语法错误。
- **高亮不用 `v-html`**：`split` 保捕获组 → 数组切片 → 模板渲染，天然免疫 XSS（用户输入 `.*`、`<script>` 都只是文本）。

## 六、几个要注意的行为（不算 bug，但要知道）

1. **类型命中等于“整类返回”**：搜“角色”会把 4 款角色扮演全给出来——这是 AC-2.2 的设计，不是模糊过头。
2. **关键词命中的类型与 `typeIds` 筛选是 AND 关系**：比如关键词命中“角色扮演”，同时筛选栏勾了“动作”，两个条件叠加后可能 0 条。想避免就把两者做成同层 OR，但会牺牲筛选的精确性。
3. **只搜 `name / name_en / 类型`**：简介 `summary`、发行商、系列名都不参与，搜"CDPR"不会有结果。类型既覆盖 `game_type_id`，也覆盖 `game_type_rel` 的标签。
4. **SQL 只去掉半角空格**：`REPLACE(...,' ','')` 对全角空格（`　`）无效；如果游戏名里混了全角空格，会出现“搜得到但归一化不一致”的极小概率问题——要更稳就把 `REPLACE` 也处理全角，或用 `REGEXP_REPLACE`。
