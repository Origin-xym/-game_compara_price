## 一、一句话链路

两条路都写同一张 `price_record`：

- **自动采集**：`POST /api/admin/collect/run?platformId&scenario` → `SourceRegistry` 按 `platform.code` 选一个采集器（**STEAM / EPIC / XIAOHEIHE**，Epic 是"浏览器渲染 + GraphQL 兜底"两个实现，Mock 兜异常场景）→ 采集器拉商店真实价 → 每条交给 `CollectPriceWriter`：校验币种/折扣 → 取汇率固化 `cny_amount` → **同价且当天已有点就跳过（跨天会补一个点）** → **偏离当前价 >50% 进"待确认队列"（status=2）** → 否则归档旧当前价 + 插入新当前价 → `status=1` 生效。
- **手动录入**：`POST /api/admin/prices` → `PriceServiceImpl.createManualPrice` 校验游戏/平台/币种/折扣一致性 → 取汇率 → 归档旧当前价 + 插入新记录（`source_type=1`）→ **直接生效，不进队列** → 写审计。

审核入口 `GET /api/admin/prices/pending` + `approve/reject` 决定队列里的采集价是否替换线上。

## 二、用到的接口（全在 `/admin/**`，`requireAdmin=true`）

| 接口 | 属于 | 作用 |
| --- | --- | --- |
| `POST /api/admin/collect/run?platformId=9&scenario=NORMAL` | 自动 | 单平台采集，返回 `total/success/queue/skip/fail/status` |

| `POST /api/admin/prices/{id}/approve` | 审核 | 通过：该价立刻变线上当前价 |

## 三、数据契约 `price_record`

| 字段 | 说明 |
| --- | --- |
| `currency / original_amount / original_price / discount_rate / discount_end_time` | 来源侧原币数据 |
| `rate / rate_time / cny_amount` | **入库即固化**的人民币价与汇率快照（AC-4.5/4.6），后续汇率变了也不回溯改价 |
| `source_type` | `1` 手动、`2` 官方 API、`3` 第三方授权 |
| `source_ref / operator` | 采集批次号 / 录入备注；`collect:批次号` 或 `admin` |
| `is_current` | `1` 当前生效；`NULL` 历史或待确认 |
| `status` | `1` 生效、`2` 待确认、`3` 已驳回 |
| `verified_by / verified_time` | 审核留痕 |
| **`uk_current(game_id, platform_id, is_current)`** | "同游戏同平台只能一条当前价"；**MySQL 唯一索引允许多个 NULL**，所以历史点和待确认可以无限多条 |

实测现状（2026-11-27）：`price_record` 共 **80 条，全部 `status=1`，其中 48 条是当前价**，**待确认队列 0 条**；按平台：Steam 44 条（22 当前）、Epic 7 条（4 当前）、小黑盒 29 条（22 当前）。最新一条 id=213 来自小黑盒（platform 11，批次 `XIAOHEIHE-CN-20261127123636`），说明**小黑盒采集已经跑通并成为主力数据源**。

## 六、工作流

**① 自动采集（手动触发）**
选平台 + 场景 → `POST /api/admin/collect/run` → 校验平台（非纯手动、已启用、已就绪）→ 生成批次号 → insert `运行中` 日志 → `SourceRegistry.find`（STEAM→`SteamPriceSource`、EPIC→`EpicBrowserPriceSource`（失败回落 `EpicPriceSource`）、XIAOHEIHE→`HeyboxBrowserPriceSource`）→ `fetch`：补 `external_id`/打开商店页 → 每条 `CollectPriceWriter.write`：

- 脏数据 → 抛异常 → 该条 `fail++`（只影响这一条）
- 与当前价相同 → `skip++`，不写历史
- 偏离 >50% → `status=2` 入队，`queue++`，**线上价不变**
- 正常 → 归档旧当前价 + 插新当前价，`success++`

→ 回填批次日志（`status` = 全部成功 1 / 部分失败 2 / 全失败 3）→ 返回 VO → 前端提示五个计数并刷新两个列表。

**② 自动采集（定时）**
每天 04:00 `CollectJob` → `runAll` → 每个就绪平台走一遍上面流程（最近一次为 id=213，小黑盒批次 `XIAOHEIHE-CN-20261127123636`）。

**③ 待确认审核**
进"待确认队列"看到 new vs current + 偏离 % → 点"通过"（确认框）→ 归档旧当前价、该条转 `is_current=1/status=1`、记审核人 → 前台立即可见新价；点"驳回" → `status=3`，线上价纹丝不动。

**④ 手动录入**
选游戏（远程搜索）→ 选平台（币种自动带出并锁定）→ 填现价/原价/折扣/截止/备注 → 确认框（明确"直接生效"）→ `POST /api/admin/prices` → 九项校验 → 汇率折算 → 归档+插入 → 审计 → 前台当前价立即更新，**不经过任何审核**。

**⑤ 前台读价（两条路的汇合点）**
列表/详情/走势/收藏都只读 `is_current=1 AND status=1` + 平台 `enabled/api_ready/deleted` —— 所以**手动与采集在读取端完全同构**，区别只留在 `source_type / source_ref / operator` 三个溯源字段。

## 七、涉及的知识点

1. **策略模式 + 注册表**：`PriceSource` 一平台一实现，`SourceRegistry` 用 `List<PriceSource>` 构造注入自动收集，**新增平台只加一个类不改编排代码**（开闭原则的落地样本）。
2. **`@Order` 决定优先级**：Epic 浏览器源 `Order(1)`、Epic GraphQL `Order(2)`、Mock `Order(100)`，再用 `enabled()` 双重开关（`app.collect.mock-enabled / steam-enabled / epic-enabled / epic-browser-enabled / heybox-enabled`），做到"关掉某一路不用改代码"。
3. **事务粒度 = 一条价格**：`write` 单独 `@Transactional`，一条失败只 `fail++`，其它条照写；整批 `fetch` 失败才全不写。**不要把整个 for 循环包进一个事务**，否则一条脏数据毁整批。
4. **唯一索引 `uk_current(game_id, platform_id, is_current)` + MySQL 的 NULL 语义**：唯一索引允许多行 NULL，所以"历史/待确认"可以无限多，而"当前价"严格唯一。**这是整个价格模型的地基**。
5. **"先归档、后插入"的固定顺序**：反过来会先撞唯一索引；且必须在同一事务里，否则出现"无当前价"的空窗。
6. **价格不变则跳过**：避免历史表被高频采集刷成噪声，也让走势图只记录"真实变化点"（AC-5.x）。
7. **波动阈值做人工兜底**：0.5 的 `|Δ|/old` 判定，把"爬虫抓错价/临时错误页/币种搞错"挡在线上之外；阈值走配置不写死。
8. **待确认去重**：同游戏+同平台+同价+`status=2` 已存在就不再入队，防管理员一天点 10 次采集堆 10 条重复。
9. **幂等 + 语义化返回码**：`write` 用 `1/0/2` 表达"写入/跳过/入队"，编排层据此分账（success/skip/queue），比抛异常更省事。
10. **批次号贯穿全链路**：`source_ref` 与 `operator` 都带 `STEAM-CN-20261124…`，任何一条线上价都能反查到批次日志。
11. **汇率固化而非实时换算**：`cny_amount` + `rate` + `rate_time` 一起入库（AC-4.5），汇率变了不回溯，历史价才稳定；无快照直接报 `EXCHANGE_RATE_UNAVAILABLE` 而不是拿 1:1 蒙。
12. **双模式同契约**：手动与采集都遵守"币种=平台结算币种、折扣率有则必须有原价、原价≥现价"，所以前台不需要区分来源就能比价。
13. **"运行中"先落库 + finally 收口 + status 默认 3**：三重保险，避免日志永远停在"运行中"。
14. **审计旁路不影响主流程**：`AuditLogService` 内部 catch（上一轮已讲），改价留痕但不会因为写日志失败让价格回滚。
15. **场景注入（`scenario`）**：`NORMAL/DROP/SPIKE/PARSE_FAIL/EMPTY` 让"异常路径"可被手动触发验证（真实源只认 NORMAL，Mock 全接），属于可测试性设计。
16. **前端"币种只读 + 平台过滤"**：把最容易出错的选择前置消灭，后端仍二次校验 —— 前端体验 + 后端边界的标准组合。

## 八、现状与坑

1. **手动录入直接生效、不进队列**：与采集路径的最大不对称。前端确认框写了这句话，但一旦误录（比如把 298 录成 29.8），线上立刻变，只能再录一次覆盖（历史还有记录，可追溯但用户已看到错价）。
2. **待确认队列没有主动通知**：只有进页面才看得到，`pending` 是个纯查询；你之前反馈的"待确认列表没有消息通知"至今没补（没有未读角标/站内信）。
3. **队列当前 0 条、全表 80 条全 `status=1`（48 条当前价）**：没有 `status=2/3` 的样本，说明"波动拦截 + 驳回"这条链路虽然有代码，但**近期没有真实触发过**；要验证得手动造一个 SPIKE 场景或改库。
4. **采集没有并发锁**：两个管理员同时点"立即采集"同一平台，或 04:00 定时与手动重叠，会出现两个批次并发 `归档+插入`，可能撞 `uk_current` → 该条 `fail++`（有日志但不友好）。缺分布式锁/单飞（`ShedLock` 或 Redis 锁）。
5. **`CollectJob` 无多实例保护**：多副本部署会每个实例都跑一遍 04:00 全量采集。
6. **`runAll` 串行 + Steam 每条 `sleep 200ms`**：游戏 100 款就是 20 秒起，平台多了会分钟级；且是同步阻塞 HTTP，占 Tomcat 线程。要提速得并发 + 限流，但会更考验 `uk_current` 的并发安全。
7. **Steam 自动补链有误绑风险**：`resolveAppId` 是"搜名字挑最佳候选"，历史上就把《文明六》绑到了 DLC 947510（现已手工改回 289070）。**新增游戏后建议人工核对 `external_id`**，别完全信任自动补链。
8. **Epic 补链已解决但要靠浏览器**：现在有三条路——Steam 导入后异步自动挂（`epic-auto-link`）、后台"补齐 Epic 链接"批量跑、链接弹窗手填；没有 slug 且浏览器也搜不到的 Epic 游戏仍永远无价。**Epic 采集依赖本机 Edge 进程**，服务器无桌面环境时只能退回 GraphQL（经常 403）。
9. **Steam 免费游戏永远无价**：`price_overview` 缺失就 `continue`，只会在详情页出"暂无报价"占位卡（这本身是设计，但用户会问"为什么这个游戏没价"）。
10. **`reject` 的记录永久滞留**：`status=3` 不进当前价、也不清理，表会慢慢变大；没有归档/清理任务。
11. **`discount_end_time` 在 Epic 路径永远是 null**：Epic 的 GraphQL 查询没带促销截止，所以 Epic 的折扣永远"长期有效"，前端不会显示"还剩 X 天"。
12. **`source_type=1` 的 `source_ref` 存的是"备注"**：备注为空时该字段为 null，溯源信息弱于采集批次号。
13. **手动录入不能改历史价**：只能新增/覆盖当前价，没有"编辑/删除某条历史记录"的接口（`AdminHistoryLowController` 只维护官方史低）。
14. **币种只能等于平台结算币种**：想录"美区 $ 折算成 ¥ 展示"必须先有 USD 结算的平台（如 STEAM/US），否则会被 40000 拦下；这也是现在全站只有 CNY 平台的原因之一。
