## 一、一句话链路

两个功能的共同点是：**折扣和风险都不单独开接口**，它们被算进「当前价」与「卡片」里，随 `GET /api/games/{id}` 一起下发（列表则是 `GET /api/games` 的 `discountOnly` 筛选 + 卡片角标）；风险数据由后台独立的 `region-risks` 接口维护。

- **折扣**：数据源头是 `price_record.discount_rate / discount_end_time / original_price`（采集自 Steam `discount_percent`，或后台手动录入）→ 服务端判断“是否仍在有效期” → 详情卡片的 `-80%` 小标签 + 划线原价、列表卡片的角标与「折扣截至」。
- **锁区风险**：数据源头是后台维护的 `region_risk` 表（平台+区域 唯一）→ 详情按 `platform.region` 匹配取**最高等级** → 卡片显示「低/中风险 · 原因」或「无锁区风险」，并决定能否点「前往商店」。

## 二、用到的接口

| 接口 | 作用 | 是否前台调用 |
|---|---|---|
| `GET /api/games/{id}` | 详情：每张卡带 `discountActive / discountRate / discountEndTime / originalPrice / rate`、`riskLevel / riskReason / riskSource / purchasable` | ✅ `GameDetail.vue` 第 37 行 |
| `GET /api/games?discountOnly=true` | 列表“只看折扣”：SQL 层 `EXISTS` 过滤 | ✅ 筛选栏 |
| `GET /api/admin/region-risks?platformId=` | 后台风险列表（含平台名、区域、等级、原因、来源、最后修改人） | ✅ 仅后台 `AdminRiskList.vue` |
| `PUT /api/admin/region-risks` | 新增/更新某平台某区域的风险（AC-6.4 后台可改） | ✅ 仅后台 |

实测（你本机）：
- `GET /api/games/12`（双人成行）：`cnyAmount 39.60 / originalPrice 198.00 / discountRate 80 / discountActive true / riskLevel 0 / purchasable true`；
- 列表里 `hasDiscount:true, maxDiscountRate:80.0`；
- `region_risk` 目前只有 `platform 1 (US, 低风险)` 和 `platform 3 (US, 高风险)`，**两条都挂在已删除的旧平台上**，所以在用的 9/10 号平台全部是 `riskLevel=0`（“无锁区风险”）。

## 五、工作流

**折扣（展示侧）**
1. 采集/录入时写入 `discount_rate / original_price / discount_end_time`（带自检回退）；
2. 详情请求 → `selectCurrentPrices` 取当前价行 → `toPlatformRow` 第 474–482 行判断是否仍有效 → 有效才下发三件套；
3. 前端：`discountActive` → `-80%` 标签 + `原价 ¥198.00`（`originalPrice*rate`）+ 截止时间；无效 → 只显示「无折扣」；
4. 列表请求 → `applyDiscount` 取该游戏“有效折扣的最大值” → 卡片角标 `-80%`。

**折扣（筛选侧）**
`discountOnly=true` → SQL `EXISTS` 只保留“有 >0 折扣且未结束”的游戏 → 列表卡片与详情口径一致。

**风险**
1. 后台在「锁区维护」页按平台+区域填等级/原因/来源 → `PUT /api/admin/region-risks` → 唯一键 upsert + 记 `updated_by`；
2. 详情请求 → `groupByPlatform` 批量取 → `pickRisk` 按当前平台 region 匹配取最高等级；
3. 卡片渲染：有风险显示彩点+等级+原因+依据，无风险显示灰点「无锁区风险」；
4. 同时算 `purchasable`，高风险平台按钮消失、换成“该区域不建议购买”。

## 六、涉及的知识点

1. **“过期”由服务端判定**：`discountActive` 在服务端算，前端只渲染布尔值。客户端时钟不可信，且列表/详情/筛选必须同一口径（SQL 里也用 `NOW()`）。
2. **无效数据兜底不抛错**：`originalPrice < amount`、折扣过期、有折扣无原价——采集器与手动录入都做“降级为无折扣”，保证脏数据不会让页面出现“原价 ¥100 现价 ¥120”的荒谬组合。
3. **划线价和实付价分开存**：`original_price`（划线）、`original_amount`（实付原币）、`cny_amount`（实付人民币），三者缺一就会算错 `originCny`。
4. **折扣率存 0 而不是 null**：让“有折扣/无折扣”只用一个 `compareTo(ZERO)>0` 判断，避免 null 判断散落各处。
5. **列表取最大折扣、详情取本平台折扣**：列表要“这游戏现在打几折”的概览（取所有平台里最大的），详情要“这张卡打几折”（取该平台自己的），两者不是同一个口径，别混。
6. **风险是“平台+区域”维度，不是“游戏+平台”**：`region_risk` 唯一键 `(platform_id, region)`，所以同平台不同区可以不同等级；`pickRisk` 只认 `platform.region`（如 `CN`），跨区风险不参与。
7. **取最高等级而非平均值**：`max(riskLevel)`，宁可提示更严重。
8. **“无风险不返回原因”**：`level=0` 时 `reason/source` 强制 null，避免前端显示“无锁区风险 · 需美区账号”这种自相矛盾（AC-6.2）。
9. **`purchasable` 是不变式**：`linkAvailable && riskLevel < 3`，按钮显隐和文案来自同一个布尔值，不会出现“高风险还能点购买”。
10. **`upsert` + 唯一键**：先按 `(platform, region)` 查，存在就 update、不存在 insert，配合唯一键天然幂等，后台重复点保存不会产生脏行。
11. **修改留痕**：`updated_by` 从 `UserContext` 取登录用户，配合 `audit_log` 可追溯“谁把这平台判成高风险”（AC-6.4）。
12. **批量查询防 N+1**：风险一次 `IN` 查全平台再 `groupingBy`，详情页只多一次 SQL。

## 七、现状与坑（和你库里数据直接相关）

1. **风险全站“无锁区风险”**：`region_risk` 只有 platform 1/3（已删），`pickRisk` 又只匹配 `platform.region`（9/10 是 `CN`）→ 全部 `riskLevel=0`。要让 Steam 显示风险，去「锁区维护」给 `STEAM / CN` 建一条；
2. **折扣目前只有 Steam 会带**：Epic 采集不可用，手动录入可以填折扣率+截止时间（`PriceServiceImpl` 第 118–130 行会校验）；
3. **`discount_end_time` 是“活动结束时间”不是“数据过期时间”**：Steam `price_overview` 不带结束时间，所以采集入库的多为 null → 前端显示“无折扣/无截止”，只有后台手动录入能补；
4. **“同价不写新点”**：`CollectPriceWriter` 第 82–85 行同价直接返回 0，所以**折扣率变化但实付价没变**时不会新增价格记录，折扣可能滞后一次采集才更新——这是后续要留意的点。
