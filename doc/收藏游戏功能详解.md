## 一、一句话链路

详情页按钮 → `POST/DELETE /api/favorites/{gameId}` 写库（`favorite` 表 `(user_id, game_id)` 唯一索引）→「我的收藏」页 `GET /api/favorites?page&size` → 后端用 `selectMyPage` 分页（SQL 里 JOIN `game.status=1`）+ 批量查当前价 → 拼成 `FavoriteItemVO`（封面、最低价、折扣、平台标签、收藏时间）→ 前端网格卡片渲染，支持取消收藏和分页。

## 二、用到的接口（4 个，都在 `/api/favorites`）

| 接口 | 鉴权 | 作用 | 返回 |
| --- | --- | --- | --- |
| `POST /api/favorites/{gameId}` | 需登录 | 收藏（**幂等**） | `null` |
| `DELETE /api/favorites/{gameId}` | 需登录 | 取消收藏（幂等） | `null` |
| `GET /api/favorites/{gameId}/exists` | 需登录 | 详情页按钮状态 | `{favorited: true/false}` |
| `GET /api/favorites?page=1&size=12` | 需登录 | 我的收藏分页 | `PageResult<FavoriteItemVO>` |

## 三、数据模型 `favorite`

| 项 | 内容 |
| --- | --- |
| 字段 | `id`、`user_id`、`game_id`、`create_time`、`update_time` |
| 唯一索引 | `uk_user_game(user_id, game_id)` ← **防重复收藏的最终防线** |
| 查询索引 | `idx_user_time(user_id, create_time)` ← 支撑"我的收藏按时间倒序" |
| 当前数据 | **0 行**（`AUTO_INCREMENT=10`，说明测试期写过 9 条后被清空） |

注意这张表**没有 `deleted` 字段**，取消收藏是物理删除。

## 六、工作流

**① 收藏**
详情页（已登录）→ 点"收藏" → `POST /api/favorites/9` → 拦截器验 token → Controller → `add(9)` → 查游戏知道 `status=1` → 查重（已存在就静默成功）→ insert → 唯一索引兜底并发 → 返回 `{code:0}` → 前端 `favorited=true`、按钮变"已收藏"。

**② 取消**
点"已收藏"或收藏页"取消收藏"（后者带确认框）→ `DELETE /api/favorites/9` → `delete where user+game` → 返回成功 → 前端翻状态 / 重拉列表（必要时回退页码）。

**③ 进入我的收藏**
点导航 → 路由守卫查 `gp_token` → 进入 `FavoriteList` → `onMounted(fetchList)` → `GET /api/favorites?page=1&size=12` → 拦截器补当前 userId → `selectMyPage`（JOIN 过滤下架 + 时间倒序 + MP 自动 LIMIT）→ 批量查类型名 + 当前价 → 逐条 `toItem`（算最低价、平台标签、有效折扣）→ 返回 `PageResult` → 渲染网格 + "共 N 款"。

**④ 详情页回来时的状态回显**
`fetchDetail()` 里若已登录，额外 `GET /favorites/{id}/exists` 拿 `favorited`，保证按钮是"已收藏"而不是每次重置。

## 七、涉及的知识点

1. **幂等的两种实现**：应用层 `selectCount` 预判（正常路径）+ 数据库唯一索引 `DuplicateKeyException`（并发兜底）。只靠前者会在双击时插两条（如果没有唯一索引）或抛 500；只靠后者则正常重复点击就变成异常流。**两层一起用才是标准写法**。
2. **用户隔离靠 ThreadLocal 而不是参数**：`UserContext.requireUserId()` 从拦截器塞进来的 `LoginUser` 取 id，接口签名里根本没有 `userId` —— 这样就不存在"前端改个 id 看别人收藏"的越权漏洞（AC-9.4）。
3. **分页要在 SQL 侧过滤**：`JOIN game ... status=1` 放进 SQL，`total` 和 `records` 就同源；如果先分页再在 Java 里 `continue` 跳过期数据，会出现"共 8 款但只显示 6 张卡"的经典 bug。
4. **MP 分页拦截器的工作方式**：`Page` 对象 + `IPage` 返回值 → 拦截器改写 SQL 加 `LIMIT`，并额外发一条 `count`。所以 XML 里**不能写行尾 `--` 注释**（第 13–18 行那段注释就是这个事故的考古记录）。
5. **N+1 查询的批量化解法**：类型名一次 `in`、价格一次 `selectCurrentPrices`、游戏一次 `in`，三次查询支撑整页 12 条，而不是 12×3 次。
6. **价格口径必须复用**：收藏页不自己写 SQL 算最低价，而是调列表页同一个 `selectCurrentPrices`，从架构上保证两处价格不可能不一致。
7. **折扣有效性判定**：`discountRate > 0` 且（无结束时间 或 结束时间 > now）——只判断 `rate > 0` 会把"去年黑五的折扣"永久标红。
8. **前端状态单一来源**：只有一个 `favorited` 布尔，按钮颜色/文案都从它派生；请求成功才翻转，避免"界面显示已收藏但库里没写"的假象。
9. **删除后的页码自愈**：第 61 行 `list.length===1 && page>1 → page--`，避免删掉当页最后一条后看到空白页。
10. **空态设计**：`el-empty` + "去逛逛"跳 `/games`，比空白页友好。
11. **`@Min/@Max` 在 `@Validated` 类上生效**：`size` 超 50 直接 400，防"一次拉一万条"的轻量 DOS。
12. **软删 vs 硬删的选择**：`favorite` 用硬删 + 唯一索引，逻辑简单；代价是没有操作审计（见下）。

## 八、现状与坑

1. **表里 0 条数据**：现在打开"我的收藏"必然空态。要演示得先在详情页点几个收藏。
2. **收藏时间是 ISO 原样输出**：`favoriteTime` 直接是 `LocalDateTime`（`2026-11-24T20:15:30`），前端第 127 行原样打印，界面上会出现那个 `T`。要好看得在 `toItem` 里 `format`，或前端 `replace('T',' ')`。
3. **没有软删/审计**：取消收藏物理删除，误点无法回溯，也没有"谁在什么时候取消"的记录。
4. **`cancel` 不校验游戏状态**：下架游戏仍能取消（这其实是好事，但和 `add` 的严格校验不对称）。
5. **收藏不产生任何联动**：既不发通知，也不影响采集/降价提醒（提醒是独立的 `alert` 模块，用户在详情页点"提醒"才建）。
6. **`gk` 双保险的微小不一致**：SQL 已按 `status=1` 过滤，Java 第 184 行又 `continue` 一次；若两条 SQL 之间有并发下架，`total` 会比实际渲染多 1，属极小概率。
7. **首屏没有"收藏数"角标**：`App.vue` 导航只有文字链接，不显示数量（要做需额外一个 count 接口或复用 list 的 total）。
8. **详情页 `isFavorited` 用了 `route.params.id` 字符串**：后端 `@PathVariable Long` 会自动转换，问题不大；但若 id 是 `abc` 会先撞 400 而不是友好的"游戏不存在"。
