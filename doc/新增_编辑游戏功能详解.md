## 一、一句话链路

后台 `AdminGameList.vue` 一个弹窗同时承担"新增/编辑"→ `POST /api/admin/games` 或 `PUT /api/admin/games/{id}` → `AuthInterceptor(requireAdmin=true)` 先验管理员 → `GameServiceImpl.createGame/updateGame` 做"名称去空格 + 重名查重 + 标签合法性（多标签）+ 空串转 null"→ 写 `game` 表 + `game_type_rel` 标签关系（唯一键 `uk_name` 兜底）→ `AuditLogService.record()` 落一条 `before/after` JSON 审计 → 返回新 id / 空 → 前端关弹窗、重拉列表。同页还挂着 Steam 一键导入、Epic/小黑盒补链、信息校验、类型标签管理四组入口。

## 六、工作流

**① 进页面**
路由 `/admin/games`（`requiresAuth`）→ `onMounted` 若无 user 先 `loadMe()` → `isAdmin?` 否 → 只显示红条提示、不发任何请求 → 是 → `GET /api/admin/games?page=1&size=10` + `GET /api/meta/types`（游戏类型）→ 渲染表格。

**② 新增**
点"新增游戏" → 弹窗表单（类型预选第一个）→ 填名称等 → 保存 → `POST /api/admin/games` → 拦截器验管理员 → `@Valid` 校验（名称必填、长度、年份范围、`typeIds≤10`）→ `createGame`：trim → 查重 → 标签解析/校验 → 空串转 null → `status=1` → insert → 写 `game_type_rel` → 写 `GAME/CREATE` 审计 → 返回 id + "新增成功" → 前端关弹窗重拉列表（新游戏出现在第一页，因为按 id 倒序）。

**③ 编辑**
点"编辑" → 该行 7 个字段回填 → 改名/改简介 → 保存 → `PUT /api/admin/games/9` → `updateGame`：查旧值 → 名称是否变化 → 变了才查重（排除自身）→ 类型校验 → 8 字段全量 set → 重新 `selectById` 作为 after → 写 `GAME/UPDATE`（before 是旧实体、after 是新实体）→ 返回成功 → 关弹窗重拉。

**④ 字段级报错回填**
后端 `40901` + `Map.of("name","该游戏已存在")` → `GlobalExceptionHandler` 把 `errors` 一起塞进 body → `request.js` reject 时挂 `e.errors` → `submit` 的 catch 写进 `fieldErrors` → `el-form-item :error` 在输入框下显示红字，弹窗不关闭（`dialogVisible` 只在成功路径置 false）。

**⑤ 上下架**
点"下架" → 确认框 → `PUT /api/admin/games/9/status?status=0` → 校验状态值 → 更新 `status` → 审计 `OFFLINE` → 提示"已下架"→ 重拉（前台列表/详情/收藏/搜索同步看不到该游戏，因为都带 `status=1` 条件）。

**⑥ 链接维护（同页）**
点"链接" → `GET /api/admin/games/{id}/links` → 每平台一行 `externalId / storeUrl / listed` → 改完点保存 → `PUT .../links/{platformId}` → 写 `game_platform` + 模板强校验（含 `{externalId}`）→ 审计 `LINK_UPDATE`。

**⑦ Steam 搜索导入（2026-11 新增）**
点"Steam 搜索导入" → 输关键词 → `GET /admin/games/steam-search` → 每个候选带 `exists/existingGameId/suggestedTypeId`：已存在的候选禁用"添加"，其余可选类型（默认候选项推荐类型）→ 点"添加" → `POST /admin/games/import-steam` → `GameImportServiceImpl`（464 行）建游戏（若已存在则复用）、绑 `STEAM` 链接、写首条当前价 → 返回 id → 重拉列表。名称/英文名/封面/简介/发行年份全部来自 Steam `appdetails`，不用手填。**导入后还会顺手挂链接**（`GameImportServiceImpl` 268 行小黑盒 `ensureLink`、273–279 行 Epic 异步 `ensureLink`，开关 `app.collect.epic-auto-link`）。

**⑧ 批量补齐与校验（2026-11 新增）**
- "补齐 Epic 链接"：`POST /epic-links/backfill`，逐款用本机浏览器搜 Epic 商店（3–5 秒/款，前端超时 300s），命中才写 `external_id`，未命中列 `NOT_FOUND`；
- "补齐小黑盒链接"：`POST /heybox-links/backfill`，直接用 Steam appId 拼 `/app/topic/game/pc/{appId}`，秒级完成，当前 22 款全命中；
- "校验游戏信息"：`POST /meta/backfill?force=`，Steam 空字段自动补、不一致只报告；勾"强制覆盖"才改写，审计记 `META_UPDATE`。

**⑨ 类型（标签）管理（2026-11 新增）**
"类型管理" → `GET /admin/game-types`（带 `usedCount`）→ 新增/编辑（`code` 自动大写、唯一，`name` ≤32）→ 删除时若仍有游戏在用（`game_type_id` 或 `game_type_rel`）会被拒绝，需先摘标签。改 code 不影响已挂标签的游戏（关联用 id）。

## 七、涉及的知识点

1. **唯一性两道防线**：应用层 `selectCount` 给友好报错，数据库 `uk_name` 兜底并发。**先 trim 再比较**是前提，否则带空格的名字能"绕过"唯一键。
2. **编辑时"改名才查重 + `ne(id)`"**：这是 CRUD 里最经典的错误点，漏了会"改简介就报重名"，或"保存原名自己撞自己"。
3. **全量覆盖（PUT）vs 局部更新（PATCH）**：这里选 PUT + 前端全量回填，语义简单；代价是**任何漏传字段会被写成 null**（见坑 1）。
4. **`blankToNull` 的三态语义**：`null`（不改/无）与 `""`（清空）在 HTTP 里容易混，这里把 `""` 与空白统一转 `null` 再 `.set()`，所以"把简介删空"能真的落库。
5. **`@Valid` + DTO 注解 = 后端唯一可信校验**：前端 `:min/:max` 只是输入辅助，`curl` 直连时全靠 `GameSaveRequest` 上的约束。
6. **字段级错误协议**：`BizException(code, message, Map<field,msg>)` → 全局处理器 → 前端 `e.errors` → `el-form-item :error`，形成"一个字段一个红字"的闭环，而不是笼统 toast。
7. **审计的 before/after 设计**：before 传**旧实体快照**、after 用**更新后重新查库**的值（第 761 行），才能如实反映"实际改成了什么"，而不是"请求里说要改成什么"。
8. **审计失败不影响主流程**：`AuditLogServiceImpl` 第 85 行吞异常 —— 日志是旁路，不能成为业务单点故障。
9. **操作人来自 ThreadLocal**：`UserContext.get()` 而不是请求参数，管理员伪造不了操作者。
10. **状态归一为 0/1 而不是布尔**：`tinyint` + 显式校验（第 773 行），前端 `row.status === 1` 判断，避免 `"0"`/`false`/`null` 三种假值混战。
11. **`@Max(50)` 限制分页大小**：配合 `@Validated` 生效，防止一次拉全表。
12. **`onMounted` 先 `loadMe` 再判角色**：Pinia 的 `user` 刷新后是 null，直接 `isAdmin` 会误判成"非管理员"并静默不加载。
13. **`payload = {...form}` 拷贝**：直接把 reactive 传给 axios 会在请求序列化时读到后续改动，拷贝是廉价保险。
14. **`fixed="right"` 操作列**：窄屏横向滚动时操作按钮永远可见，后台表格的常见细节。

## 八、现状与坑

1. **PUT 是"全量覆盖"，漏字段就会被清空**：`updateGame` 第 869–885 行无条件 `.set(...)`。前端 `openEdit` 全量回填所以页面操作安全；但用 Postman/脚本只传 `{"name":"x","typeIds":[2]}` 会把 `nameEn/coverUrl/summary/sortWeight` 全部抹成 null/0。**`typeIds` 更是先删后插**（888 行 → `saveTypeRels`），漏传就等于把该游戏的标签全摘光。
2. **`createGame` 没 catch `DuplicateKeyException`**：两个管理员同时提交同名游戏，应用层查重可能都通过，第二个 insert 撞 `uk_name` → 抛到全局处理器 → **50000 系统错误**，而不是"该游戏已存在"。
3. **`sortWeight` 后端零校验**：DTO 第 39 行没有任何注解，负数、`Integer.MAX_VALUE` 都能进库（前端 `:min="0"` 只是 UI 约束）。
4. **后台列表直接返回 `Game` 实体**：没有 `AdminGameVO`，字段全量暴露（`summary` 1000 字也一起传）；现在已经额外补 `gameTypeIds`，以后 `game` 表加内部字段会顺手泄露给前端。
5. **没有删除接口**：只有上下架。`game` 表也没有 `deleted` 列，真要删只能手工 SQL/后台脚本，且收藏、价格、提醒会变孤儿数据。
6. **下架是"软隐藏"**：`status=0` 后前台列表/搜索/详情/收藏全部过滤掉（AC-11.3），但 `price_record` / `favorite` / `alert` 数据都保留，重新上架即刻恢复。
7. **`releaseYear` 允许到 2100**：`@Max(2100)` 是"够用"的粗暴上限，能录入 2099 年"未发行"的年份。
8. **无封面 URL 格式校验**：`coverUrl` 只校验长度，`javascript:`、相对路径、非法域名都能存；详情页 `img src` 大多数情况只是裂图，但后台应加 `http(s)` 前缀/域名白名单。
9. **`updateGame` 不改 `status`**：编辑接口会写 `sortWeight`，但**不会**写 `status`（走独立接口），所以"编辑弹窗里改不到上下架"是设计而非 bug。
10. **`changeStatus` 的 `status != 0 && status != 1`** 依赖 `Integer` 拆箱（993 行已先判 null），若传 `2` 会被拦为 `40000`；这条校验只在这个方法里。
11. **审计表无清理策略**：`GAME/LINK_UPDATE` 已经 72 条，随运营线性增长，没看到归档/分区设计。
12. **`keyword` 只在 `name`/`nameEn` 上 like**：搜类型名、搜 id 都不支持；且 `like` 走 `%kw%` 无法用 `uk_name` 索引，数据量大时会全表扫。
13. **Steam 导入的类型是"猜"的**（2026-11 新增）：`suggestedTypeId` 来自 Steam 分类到本地标签的映射，映射不到时回落"第一个类型"；导入后如果类型不对，去编辑弹窗手动改标签。
14. **Epic 补齐很慢且不可并行**（2026-11 新增）：逐款串行开浏览器，22 款约 1–2 分钟；前端超时已放宽到 300s，但如果后端进程被重启，结果弹窗会拿到空列表，属于"部分成功不可续"的已知限制。
