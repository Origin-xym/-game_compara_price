## 一、整体链路一句话

`GameList.vue`（一个 `filters` 状态对象）→ `listGames()` → axios `/api/games` → `GameController.list()` → `GameServiceImpl.listGames()` → 一次分页 SQL + 两次批量补数 → `PageResult<GameListItemVO>` → 前端渲染 `GameCard` 网格。

## 二、这个功能涉及的 3 个接口

表格

| 接口                                                         | 用途                                 | 实测返回（节选）                                             |
| ------------------------------------------------------------ | ------------------------------------ | ------------------------------------------------------------ |
| `GET /api/games?page&size&keyword&typeIds&platformIds&priceMin&priceMax&discountOnly` | 列表主接口：搜索 + 筛选 + 分页       | `{total:6, page:1, size:2, totalPages:3, hasMore:true, list:[{id:13,name,minPriceCny:149.0,hasQuote:true,...}]}` |
| `GET /api/platforms`                                         | 筛选项：平台下拉（只返回前台可用的） | `[{id:9,code:"STEAM",name:"Steam",region:"CN",currency:"CNY"}, …]` |
| `GET /api/game-types`                                        | 筛选项：类型下拉                     | 3 条类型                                                     |

> 注意：`typeIds` / `platformIds` 前端是逗号串（`2,3`），后端 `List<Long>` 靠 Spring 的类型转换自动拆开，不需要手写解析。

## 四、一次点击的完整工作流

1. **交互**：改搜索框 / 筛选 → `filters` 变 → `applyConditions()` 把 `page=1` → `fetchList()`；
2. **组参**：`buildParams()` 生成 `{page,size,keyword,typeIds:"2,3",platformIds:"9",priceMin,priceMax,discountOnly}`；
3. **发请求**：axios 补 baseURL `/api` + token → Vite 代理到 `localhost:8081`；
4. **入参校验**：Spring 用 `@ModelAttribute` 把 query 绑成 `GameListQuery`（`typeIds=2,3` 自动转 `List<Long>`），`@Valid` 校验 `size≤50` 等，失败由全局异常处理器转成 `PARAM_INVALID`；
5. **业务前置**：`listGames` 先判 `priceMin ≤ priceMax`，再 `prepareKeyword` 规范化 + 查类型命中；
6. **查库**：`new Page<>(page,size)` + `selectAppPage` → MyBatis-Plus 分页插件在校验完 SQL 后自动拼 `LIMIT` 并执行 `count`（一次调用拿到 `records + total`）；
7. **批量补数**：对当页 id 做两次 `IN` 查询（类型名、当前价），内存里 `groupingBy` 组装；
8. **装 VO**：每款游戏算 `minPriceCny`、平台标签、折扣；无价给 `null`；
9. **回传渲染**：`PageResult.of(total, page, size, items)` → `Result.ok` → 拦截器解包 → `list/total` 赋值 → `GameCard` 网格 + 分页条。

## 五、这套写法里的关键知识点

- **分层**：`Controller`（HTTP 入出）/ `DTO`（只接参数）/ `Service`（业务）/ `Mapper`（SQL）/ `VO`（只出视图）。实体 `Game` 不出接口，避免把 `status`、`sort_weight` 之类内部字段暴露给前台。
- **参数绑定**：`@ModelAttribute` 对 GET 查询串，`List<Long>` 支持逗号串自动拆分；`@Valid` 放在 DTO 字段上，`@Validated` 放类上才生效。
- **动态 SQL**：`<if>` 拼条件、`<foreach>` 拼 `IN`、`<sql id>` + `<include>` 复用表达式 —— 这是 `minPriceExpr` 能被 “筛选” 和 “排序” 共用的原因。
- **口径单一化**：`minPriceExpr`、`selectCurrentPrices`、视图 `v_game_min_price` 三处必须同口径，否则会出现 “列表 ¥22、详情 ¥148” 的自相矛盾。
- **分页**：`IPage` + `Page` 是**物理分页**（SQL 层 `LIMIT`），不是 `LIMIT` 到内存再切；`total` 由插件单独发 count。
- **避免 N+1**：一页 12 条如果逐条查类型 / 价格就是 25 次 SQL；这里固定 3 次（主查询 + count、类型、价格）。
- **空值语义**：“无报价” 用 `hasQuote=false + minPriceCny=null`，而不是 `0`，否则会被当成 “免费游戏”。
- **前端状态管理**：`filters` 是唯一真相，标签、请求参数、清空逻辑全部从它派生，所以 “撤销一个条件” 只改数组再重查，不用维护多份状态。
- **axios 拦截器**：把 `{code,message,data}` 统一解包，页面拿到的就是 `data`；`401xx` 统一跳登录，业务代码不用每处判断。
- **computed + 分段渲染**：`highlightParts` 返回 `[{text,hit}]`，模板 `v-for` 渲染，避免 `v-html` 注入风险。

## 六、几个真实存在的坑（你这套代码里已经踩过 / 还在）

1. **口径漂移**：之前平台从 1/2/3/4 收敛到 9/10 时，三处 SQL 里任何一处漏改，列表起价和详情最低就会不一致 —— 改口径必须三处一起改。
2. **逻辑删除依赖物理 `deleted` 列**：`pf.deleted=0` 是直接写在 SQL 里的，`@TableLogic` 只对 MyBatis-Plus 自动生成的语句生效，所以手写 XML 必须自己带。
3. **列表没有缓存**：目前每页都实打实查库（Redis 只在通知 / 热点里用），数据量上来后建议把 “平台 + 类型” 字典和首页第一页做短 TTL 缓存。
4. **`size` 上限 50**：`GameListQuery` 第 21 行，前端要一次拉更多会直接 400，别想着 `size=200` 绕分页。
