## 一、一句话链路

注册/登录 → 后端校验后签发 **JWT**（`HS256` + `jti`）→ 前端把 token 存 `localStorage.gp_token` → 之后每个请求由 axios 拦截器塞 `Authorization: Bearer xxx` → 后端 `AuthInterceptor` 校验签名/过期/黑名单/角色，并把用户身份塞进 `UserContext`（ThreadLocal）→ 业务代码用 `UserContext.require()` 取当前用户；登出把 `jti` 写进 Redis 黑名单，让旧 token 立刻失效。

## 二、用到的接口（4 个，都在 `/api/auth` 下）

| 接口 | 鉴权 | 作用 | 返回 |
| --- | --- | --- | --- |
| `POST /api/auth/register` | 公开 | 注册并**自动登录** | `{token, expiresAt, user:{id,username,nickname,role}}` |
| `POST /api/auth/login` | 公开 | 登录 | 同上 |
| `POST /api/auth/logout` | 需登录 | 登出（把 jti 拉黑） | `null` |
| `GET /api/auth/me` | 需登录 | 取当前用户（前端启动时恢复会话） | `UserVO` |

实测库里现有两个账号：`testuser`（`role=2` 管理员）、`xym009621`（`role=1` 普通用户），密码库是 `$2a$10$…` 的 BCrypt 密文。

## 三、数据模型 `sys_user`

| 字段 | 说明 |
| --- | --- |
| `username` | 唯一键 `uk_username`，4–20 位字母/数字/下划线 |
| `password_hash` | BCrypt 密文（`varchar(100)`），**永不明文** |
| `nickname / email / phone` | 昵称必填兜底为用户名；邮箱/手机预留未启用 |
| `role` | `1` 普通用户 / `2` 管理员（AC-11.5） |
| `status` | `1` 正常 / `0` 禁用（登录时拦） |
| `failed_count / locked_until` | 连续失败计数与锁定到期时间（防爆破） |
| `last_login_time / deleted` | 最后登录、逻辑删除 |

## 五、五条工作流

**① 注册**
表单（前端长度/字符规则）→ `POST /register` → 后端 `@Valid` 复核 → 用户名查重 → BCrypt 加密 → 插库（role=1/status=1）→ 立即签发 JWT → 返回 `LoginVO` → 前端存 token + user → 跳回 `redirect` 或 `/games`。

**② 登录**
`POST /login` → 查用户（不存在也给同一个 `LOGIN_FAILED`）→ 状态/锁定检查 → 密码 `matches` → 失败则计数（5 次锁 15 分钟）→ 成功则清零计数、更新最后登录 → 签发 JWT（`jti`+`role`）→ 前端存 token。

**③ 访问受保护接口**
`/admin/**` 或 `/favorites/**` 等 → 拦截器：头缺失/格式错 → 401；签名失败 → `TOKEN_INVALID`；过期 → `TOKEN_EXPIRED`;`jti` 在 Redis 黑名单 → 拒绝；`/admin/**` 还要 `role==2` → 写入 `UserContext` → Controller/Service 用 `UserContext.require()` 取当前用户（如审计日志的 `updated_by`）→ 请求结束 `UserContext.clear()`。

**④ 登出**
`POST /logout` → 解析 token 得 `jti + exp` → `SETEX auth:blacklist:{jti} ttl` → 前端清 token/user → 即使别人拿到旧 token，在剩余有效期内也会被黑名单拦下。

**⑤ 会话过期**
前端任何请求收到 `401xx` → `request.js` 清 `gp_token` 并 `location.href = /login?redirect=...` → 重新登录。

## 六、涉及的知识点

1. **无状态 JWT + 有状态黑名单**：JWT 本身不可撤销，所以用 Redis 存“已登出 jti”，且 TTL = token 剩余寿命——过期自动清理，不占内存。
2. **`jti` 的作用**：没有它就没法做“精确吊销单个 token”；`subject=userId` 便于取身份，`role` 放 claim 避免每请求查库。
3. **BCrypt 强度 10**：自带盐、可调 cost，`matches` 内部比较；存 `varchar(100)` 是因为 BCrypt 密文固定 60 字符。
4. **防用户名枚举**：用户不存在、密码错都给 `LOGIN_FAILED`；但“禁用/锁定”必须给不同提示（否则用户不知道该怎么办），这是安全与体验的折中。
5. **失败计数 + 锁定**：`failed_count` 与 `locked_until` 落在**用户表**而不是内存/Redis，重启不丢；成功后必须清零（AC-8.6）。
6. **ThreadLocal 必须清**：`afterCompletion` 里 `UserContext.clear()`，否则线程池复用会把 A 的身份带给 B（最典型的生产事故）。
7. **两级鉴权**：前端 `v-if="isAdmin"` 只是体验优化，真正边界在拦截器 `requireAdmin`（AC-11.5 明确“前端隐藏是第二道”）。
8. **CORS + Bearer**：token 放 header 而不是 Cookie，天然免疫 CSRF；代价是必须 `allowCredentials` 配套 `allowedOriginPatterns`（不能用 `*`）。
9. **`@TableLogic` 与登录**：`SysUser` 有 `deleted`，但 `login` 用 `selectOne` 会自动带 `deleted=0`，所以软删账号登不进来。
10. **DTO 校验 vs 前端校验**：前端只做即时提示，真正的规则在 `RegisterRequest` 的 `@Pattern` 上；密码正则 `[\x21-\x7E]` 排除空格，避免前后端 trim 不一致。
11. **接口分层**：`AuthController` 只做协议，`AuthService` 做策略（阈值/锁定/黑名单），`JwtUtil` 纯工具，`AuthInterceptor` 纯鉴权——改策略不动协议。

## 七、现状与坑（你这套代码里真实存在的）

1. **改密码/被禁用后旧 token 仍然可用**：拦截器只验签名+黑名单+角色，**不查库**（只有 `/auth/me` 会查）。所以管理员把某账号 `status=0` 后，该用户手里的 token 在 120 分钟内照样能调收藏/提醒接口。要堵就得在拦截器加一层 Redis 用户版本号或短 TTL。
2. **没有 refresh token**：`expire-minutes: 120`，到期必须重登；`expiresAt` 前端也没用来提前提醒。
3. **token 存 localStorage**：任何 XSS 都能直接读走；更稳的是 httpOnly Cookie + CSRF token（但会引入 CSRF 复杂度）。
4. **管理员账号靠手工种子**：库里只有 `testuser`（role=2）和 `xym009621`（role=1）；没有“申请管理员/后台提权”的接口，`role` 只能改库。
5. **注册只有用户名密码**：`email/phone` 字段建了但接口不接收，也没有验证码/邮件验证，属于 Q6 未定项。
6. **`ADMIN_ONLY`/`TOKEN_EXPIRED` 的提示依赖前端**：前端只按 `401xx` 区间统一跳登录，`403xx`（如 `ADMIN_ONLY`）只弹错误不跳转——普通用户误点后台链接会看到“无权限”红字而不是被引导，这是可优化点。
