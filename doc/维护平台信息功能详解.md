## 一、一句话链路

后台「平台信息」页 → `GET /api/admin/platforms`（全量，含禁用/未就绪/已删的仍在表里被过滤掉）→ 弹窗新增/编辑 → `POST` / `PUT` → `PlatformAdminServiceImpl` 做**归一化（code/region/currency 大写）+ 唯一键 `code+region` 校验 + 派生约束（仅手动 → apiReady 强制 0）** → 写 `platform` 表（`deleted` 是 `@TableLogic` 逻辑删除）→ 每次写操作落审计；删除后再用同 `code+region` 新建，会走 `restore` 把旧行**复活**而不是撞唯一键。

启停/删除/就绪三个开关共同决定"该平台的价格是否进入全站口径"（列表/详情/走势的 SQL 都带 `enabled=1 AND api_ready=1 AND deleted=0`）。

## 二、用到的接口

| 接口 | 作用 | 返回 |
| --- | --- | --- |
| `GET /api/admin/platforms` | **全量**平台（不隐藏禁用/未就绪），带统计 | `List<AdminPlatformVO>` |
| `POST /api/admin/platforms` | 新增（同 code+region 曾被删 → 自动恢复） | `data = id` |
| `PUT /api/admin/platforms/{id}` | 编辑（**返回 String 提示语**，不是 VO） | `data = "币种已变更…"` |
| `PUT /api/admin/platforms/{id}/status?status=0\|1` | 启用/禁用 | `null` |
| `DELETE /api/admin/platforms/{id}` | 逻辑删除 | `"平台已删除（历史数据保留…）"` |
| `GET /api/platforms`（前台，`PlatformController` 36–40） | 前台筛选项 | 只含 `enabled=1 AND api_ready=1` |

前 5 个全在 `/admin/**` → `requireAdmin` 拦截（`40301` 拒绝非管理员）；第 6 个是公开接口（`listFrontOptions` 第 43–50 行两个条件 + id 升序）。

## 三、数据模型 `platform`（实测 9 行，4 条已删）

| 字段 | 说明 |
| --- | --- |
| `code` + `region` | **`uk_code_region` 唯一键**（`STEAM/CN` 与 `STEAM/US` 是两个平台） |
| `name` | 展示名 |
| `currency` | 该区域结算币种，`char(3)`，手动/采集都要求"录入币种 = 它" |

| `enabled` | 是否启用，默认 1；禁用**立即退出最低价/走势/采集** |

| 索引 | `uk_code_region`、`idx_enabled` |

实测数据（2026-11-27）：`1 STEAM/US`、`2 EPIC/US`、`3 XBOX/US`、`4 STEAM/HK` 全部 `enabled=0 deleted=1`；`9 STEAM/CN`、`10 EPIC/CN`、`11 小黑盒/CN` 为 `enabled=1 api_ready=1`；`12 杉果/CN`、`13 steampy/CN` 为 `enabled=1` 但 `api_ready=0`。所以**前台筛选项只有 3 个**（9/10/11），后台列表能看到 5 个可用 + 4 个已删。

## 六、工作流

**① 新增平台**
点"新增平台" → 填 code/name/region/currency/链接模板/数据源类型 → 保存 → `POST /api/admin/platforms` → `@Valid`（编码 2-10 位、区域 2-4 位、币种 3 位）→ `fill` 归一化 + 模板占位校验 + 类型 1–3 → **先查"同 code+region 是否曾被删"**：

- 是 → 复活那行（保留 id 与历史关联，`deleted=0`，字段按新表单刷新）→ 审计 `RESTORE_PLATFORM`
- 否 → `ensureUnique` → insert → 审计 `CREATE_PLATFORM`

→ 返回 id → 前端提示"平台已创建"→ 重拉列表（新平台"未就绪"默认 0，所以还不会出现在前台）。

**② 编辑平台**
点"编辑" → 回填 9 个字段 → 改币种/区域/链接模板/就绪/启用 → 保存 → `PUT /api/admin/platforms/{id}` → 查旧值 + 快照 → 判断币种/区域是否变化 + 数历史条数 → `fill` + `ensureUnique(excludeId=id)` → 只更新 `platform` 表 → 审计 `UPDATE_PLATFORM`（before/after 快照）→ **返回提示语** → 前端把提示语直接 toast 出来（"币种已变更为 CNY；历史 44 条价格记录保留原币种与汇率快照不改写…"）。

**③ 启用 / 禁用**
点 switch → 确认框 → `PUT /{id}/status?status=0` → 0/1 校验 → 只改 `enabled` → 审计 → 前台**立即**变化：

- 禁用：该平台所有价从"最低价/平台卡片/走势/前台筛选项"消失，采集也会被拒（`平台已禁用`），但 `price_record` 一条不删
- 启用：立刻重新参与全站最低价

**④ 删除（逻辑删除）**
点"删除" → 确认框（讲清"历史保留、可重建恢复"）→ `DELETE /{id}` → `@TableLogic` 置 `deleted=1` → 审计 `DELETE_PLATFORM`。此后该平台的 `price_record`、`game_platform`（含 `external_id`/`store_url`）、`region_risk`、`historical_low` **全部还在库里**，只是被 SQL 的 `deleted=0` 过滤掉。

**⑤ 删了再建（恢复）**
用相同 `code+region` 新增 → `selectByCodeRegionIgnoreDeleted` 命中 `deleted=1` 那行 → `restore` 置 `deleted=0` 并刷新字段 → **id 不变** → 之前挂在它名下的历史价、游戏链接、区域风险**自动重新生效**（不用重新绑定 `external_id`）。

**⑥ 前台口径联动**
列表/详情/走势/收藏/前台筛选的 SQL 都带 `enabled=1 AND api_ready=1 AND deleted=0` → 三个开关任一不满足，该平台的价格就整体"退出战斗"，且**不会留下 ¥0 或空行**（占位卡只认 `listed=1` + `enabled=1`）。

## 七、涉及的知识点

1. **逻辑删除 + 唯一索引的冲突**：`uk_code_region` 是硬约束，删了再建会撞 1062。解法是"自定义裸 SQL 绕过 `@TableLogic` 查已删行 → 原地 `restore`"，既保住关联数据，又不破坏唯一键。这是这模块最有价值的一处设计。
2. **`@TableLogic` 的隐式过滤**：`selectById/selectList/updateById` 自动加 `deleted=0`，所以普通代码**看不到**已删行；要看到必须用自定义 `@Select`（第 20 行）。知道这一点才不会写出"为什么我查不到刚删的那条"。
3. **两张"删除"语义并存**：平台 = 逻辑删除（可恢复、保历史）；游戏 = 只有上下架（没有 `deleted` 列）。同一系统里两种策略，取决于"删了会不会破坏历史数据"。
4. **归一化的单点收口**：所有写路径都必须经过 `fill`（code/region/currency 大写 + trim），否则"steam/cn"和"STEAM/CN"会变成两个平台，唯一键形同虚设。
5. **派生字段的强制约束**：`dataSourceType=3` → `apiReady` 强制 0（第 205–207 行），保证"仅手动平台永远进不了前台"，而不是指望运营记得关开关。
6. **不合法入参的"降级"而非报错**：`apiReady/enabled` 传了非法值 → 新增用默认、编辑沿用旧值，而不是 400。对"可选开关"这是合理宽容；对 `dataSourceType` 则严格报错（它决定业务分支）。
7. **变更币种只影响未来**：第 128–134 行的提示语是这套设计的产品化表达 —— `price_record.cny_amount` 与 `rate/rate_time` 已固化，**改平台币种不回溯历史**（AC-13.3），否则历史最低价会被"重算"成假数据。
8. **`Result<String>` 当提示通道**：service 返回字符串、controller 原样带回、前端直接 toast，省掉一个专门的"变更影响"字段；代价是接口返回类型不统一。
9. **接口层不校验、service 校验**：DTO 只管"格式"（长度/正则），"语义"（模板必须含占位、类型范围、仅手动→未就绪）全在 `fill` 里，保证任何调用方（页面/脚本）都过同一套规则。
10. **`el-switch + @click.prevent`**：不用 `v-model` 直接绑定（否则 UI 先变、请求失败就假状态），而是"点了先弹确认、成功再重拉"，**UI 状态永远来自服务端**。
11. **审计快照用 Map 而非实体**：只记业务字段，diff 干净、不把时间戳噪声塞进 JSON。
12. **平台是三处口径的共同开关**：`platform.enabled/api_ready/deleted` 同时控制"展示、最低价、采集、手动录入、前台筛选"五个行为，是典型的"一处配置、全链路生效"。
13. **`hasHistory` 作为前端提示依据**：后端算好"有没有历史价"（67 行），前端才知道要不要显示"变更币种不改写历史"的黄字 —— 让 UI 的警示有数据依据，而不是无条件吓人。

## 八、现状与坑

1. **`listAll` 是 N+1 查询**：9 个平台 = 1 次列表 + 18 次 count。平台数量小所以无感，但要扩到几十个会明显变慢；正解是一次 `GROUP BY platform_id` 拿两个计数。
2. **改 `code` 会切断采集器**：`SourceRegistry` 按 `platform.code` 匹配采集器（`STEAM`/`EPIC`），把 code 从 `STEAM` 改成 `STEAM2` 后，该平台立即"暂无可用采集器"。而编辑弹窗里 code 是**可改的**（`fill` 会覆盖），没有二次确认。
3. **`linkTemplate` 只校验"含 `{externalId}`"，不校验 URL scheme**：`javascript:...{externalId}` 这种能存进库，前台 `window.open` 会执行。此前讲过这个安全留白，仍未加固。
4. **删除平台的连带影响是"静默"的**：`price_record / game_platform / region_risk / historical_low` 全都留着但被过滤 —— 你之前遇到的"官方史低全站为空"就是因为 `historical_low` 两条数据挂在已删的 platform 1/3 上。**删平台前应先看"历史 N 条"这个计数**，页面虽然展示了，但没有强制提醒。
5. **`restore` 不重置 `create_time`**：恢复后"创建时间"还是旧的，审计里会出现"创建于很久以前、最近又恢复"的时间线；语义上没错，但报表统计"新增平台数"时会失真。
6. **`restore` 只刷新 8 个字段，不校验 `code/region` 大小写**：`fill` 已归一化，所以问题不大；但恢复路径**跳过了 `ensureUnique`**（因为本来就是同一行），如果有人手工改过库导致重复行，这里不会拦。
7. **`changeStatus` 不检查"是否还有当前价"**：禁用有价的平台是允许的（只是全部退出前台），没有提示"该平台还有 3 条当前价将不可见"。产品上可接受，但运营容易困惑。
8. **`apiReady` 没有独立快捷开关**：表格里只有 `enabled` 的 switch，"就绪"必须进编辑弹窗改。而"未就绪"是平台退出前台的**必要条件之一**，容易被忽略（新增平台默认 `apiReady=0`，忘了打开就一直不上线）。
9. **`update` 允许把 `apiReady` 从 1 改回 0**：这会瞬间让该平台所有价从全站消失，无二次确认（`enabled` 的切换有确认，`apiReady` 没有）。
10. **前台筛选项与后台列表口径不同**：`/api/platforms` 只给 `enabled=1 AND api_ready=1`，所以后台能看到 5 个可用的（9–13）+ 4 个已删的；前台只看得到 **3 个（9/10/11）**，杉果/steampy 因为 `api_ready=0` 进不来。
11. **没有"平台排序"字段**：前台筛选项按 id 升序，想调顺序只能改 id/重建。
12. **删除无"回收站"入口**：恢复只能靠"同 code+region 再新增一次"，运营不知道这个暗门（提示语里有写，但只有删除时那一瞬间能看到）。
