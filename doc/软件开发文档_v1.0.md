# 1 引言

## 1.1 编写目的

本文档是「游戏跨平台比价系统」的软件开发文档，作用有四个：

1. **代码与需求的对账基线**：说明系统“做了什么、为什么这样做”，任何后续改动都要先在本文件对应章节登记。
2. **交接材料**：新成员按第 4 章理解架构、按第 5～6 章定位代码、按第 8 章把系统跑起来。

4. **风险台账**：第 10 章集中登记已知缺陷与技术债，避免“口头知道、文档没有”。

## 1.3 术语与缩略语

| 术语 | 含义 |
|---|---|
| 统一口径 | 全站唯一的“有效价格”定义：`price_record.is_current=1 AND status=1`，且平台满足 `enabled=1 AND api_ready=1 AND deleted=0` |
| 当前价 | 某游戏在某平台唯一生效的一条价格记录（`is_current=1`） |
| 历史点 | 同一游戏同一平台的历史采样，`is_current=NULL`，用于走势 |
| 史低（真实） | 该游戏所有生效历史点中的最低人民币价，由 `price_record` 实时聚合（`lowestEverCny`） |
| 史低（官方） | 第三方授权源给出的官方史低，独立存 `historical_low`，仅展示、不参与最低价 |
| 占位卡 | 后台已维护“该平台上架”但取不到价格时，详情页展示的“暂无报价”卡片 |
| 待确认 | 采集价与当前价偏离超过阈值时，写入 `status=2` 的价格记录，等管理员审批 |
| 批次号 | 一次采集任务的唯一标识，形如 `STEAM-CN-20261124155453-8987`，同时写入 `price_record.source_ref` |
| 锁区风险 | 某平台某区域对中国区玩家的购买/激活限制等级（0 无 / 1 低 / 2 中 / 3 高） |
| AC | 验收标准（Acceptance Criteria）条目编号，见《游戏比价网站_验收标准_v0.3》 |

# 2 项目概述

## 2.1 项目背景

同一款游戏在 Steam、Epic、小黑盒、杉果、SteamPy 等渠道的价格、折扣时间、结算币种各不相同；玩家要比价往往需要开五个页面，还要自己按当天汇率换算。与此同时，“是不是史低”“有没有锁区风险”“这个折扣还剩几天”这些判断信息分散在第三方工具里，可信度和时效性都不稳定。

系统要解决的问题就是把这五件事收敛到一张卡片上：**当前最低人民币价、各平台逐条报价、价格走势、史低标注、折扣与锁区风险**。

## 2.2 建设目标

| 编号 | 目标 | 可度量标准 |
|---|---|---|
| G1 | 一个页面看全网最低价 | 列表页每张卡片直接给出“最低人民币价 + 折扣率 + 平台标签” |
| G2 | 价格可比、可追溯 | 所有价格按统一口径折算为人民币并固化汇率快照，任意价格可追溯到批次号/录入人 |
| G3 | 数据可持续更新 | 支持官方数据源自动采集（Steam、Epic）与人工录入双模式；每日 04:00 自动全量采集 |
| G4 | 口径唯一 | 列表起价、详情最低价、收藏最低价三处使用同一段 SQL 表达式，不允许各写一份 |
| G5 | 可运维 | 后台可维护平台、游戏、链接、史低、锁区风险；所有写操作留痕；采集有批次日志 |

## 2.3 系统范围

**本期实现（In Scope）**

- 游戏主数据维护与前台检索（名称、类型、平台、价格区间、仅看折扣）
- 游戏详情：多平台价格对比卡片、多平台价格走势（一平台一条折线）、史低标注
- 折扣信息与区域锁区风险提示
- 跳转官方商店（模板生成 + 后台可覆盖）
- 注册、登录、登出、当前用户信息（JWT）
- 收藏、我的收藏
- 降价提醒（目标价 / 跌至史低 / 任意降价）与站内通知
- 后台：游戏管理、平台管理、游戏平台链接管理、价格手动录入、待确认审批、史低维护、锁区风险维护、采集触发与日志、一致性自检、审计留痕
- 定时任务：每日采集、每分钟提醒判定

**本期不做（Out of Scope）**

| 不做的事 | 原因 |
|---|---|
| 站内购买、下单、支付 | 比价工具定位，交易涉及支付合规与渠道协议 |
| 对接平台账号、读取用户库 | 涉及第三方账号授权与隐私合规 |
| 绕过反爬的抓取 | 合规风险；只使用官方公开接口或授权源 |
| 移动端 App、小程序 | 本期只交付 Web |
| 多币种前台展示 | 已确定只展示人民币（2026-11-21 变更） |
| 推荐算法、社区、评论 | 不在本期验收范围 |

## 2.4 用户角色

| 角色 | 权限边界 | 典型操作 |
|---|---|---|
| 游客 | 只能读公开接口 | 浏览列表、搜索、看详情与走势 |
| 注册用户（role=1） | 公开接口 + 个人数据接口 | 收藏、设提醒、看通知、看我的收藏 |
| 管理员（role=2） | 全部接口（含 `/admin/**`） | 维护游戏/平台/价格/链接/风险，触发采集，审批待确认 |
| 系统（定时任务） | 无 HTTP 身份 | 04:00 采集、每 60s 判定提醒 |

> 权限判定在服务端拦截器完成，前端隐藏菜单只是体验优化，不作为安全边界。

## 3.2 业务规则

| 编号 | 规则 | 实现位置 |
|---|---|---|
| BR-01 | 有效价格 = `is_current=1 AND status=1`；平台必须 `enabled=1 AND api_ready=1 AND deleted=0` | `GameMapper.xml#minPriceExpr` 与 `PriceRecordMapper.xml#selectCurrentPrices`（两处必须完全一致） |
| BR-02 | 同游戏同平台最多一条当前价，靠唯一索引 `uk_current(game_id, platform_id, is_current)` 保证；历史点 `is_current=NULL` 因此不受限 | `schema.sql`、`CollectPriceWriter` |
| BR-03 | 写入当前价必须先归档（旧 `is_current→NULL`）再插入新行，否则撞唯一索引 | `CollectPriceWriter.write`、`PriceServiceImpl` |
| BR-04 | 前台最低价只由 `price_record` 聚合得出，`historical_low` 表不得参与 | `minPriceExpr` |
| BR-05 | 走势只取 `status=1` 的采样点（不要求 `is_current=1`），少于 2 个点时只画点不连线 | `PriceTrendServiceImpl.getHistory`、`PriceChart.vue` |
| BR-06 | 折扣率 = `discount_percent`；无折扣时 `original_price = original_amount` | 采集器与 `PriceServiceImpl` |
| BR-07 | 跳转链接优先级：`game_platform.store_url` > `platform.link_template` 替换 `{externalId}` | `ShopLinkBuilder` |
| BR-08 | 采集价与当前价偏离 > 50%（`app.collect.volatility-threshold`）→ 写 `status=2` 待确认，不覆盖线上价 | `CollectPriceWriter.write` |
| BR-09 | 同价重复采集：当天已存在 `status=1` 采样点则跳过，否则补写一条（保证走势每天至少有 1 个点） | `CollectPriceWriter.write`（B 方案） |
| BR-10 | 提醒去重：同一价格不重复通知，价格回升后不重复通知，只有创新低才再次通知 | `AlertCheckJob.evaluate` + `alert_rule.last_fired_price` |
| BR-11 | 目标价必须严格低于当前最低价，否则拒绝创建 | `AlertServiceImpl.create` |
| BR-12 | `data_source_type=3`（仅手动）的平台强制 `api_ready=0`，永不进入有效价格 | `PlatformAdminServiceImpl.fill` |
| BR-13 | 链接模板必须包含 `{externalId}` 占位符 | `PlatformAdminServiceImpl.fill` |
| BR-14 | 逻辑删除后可用“同编码 + 同区域”重新创建，此时走复活分支并保留原 ID（历史价不丢） | `PlatformAdminServiceImpl.create` |
| BR-15 | 所有后台写操作必须留痕；留痕失败只记录日志，不影响主流程 | `AuditLogServiceImpl.record` |

# 4 总体设计

## 4.1 设计原则

1. **口径唯一**：涉及“最低价”的 SQL 只有两处，且必须逐字一致；任何新查询复用 `minPriceExpr` / `selectCurrentPrices`。
2. **数据可追溯**：价格记录带来源类型、批次号、汇率与汇率时间；后台操作带前后镜像。
3. **失败可降级**：采集单条失败不影响整批；整批失败保留旧价；审计失败不影响业务。
4. **约定优于配置**：逻辑删除、时间戳自动填充、分页上限统一由框架层兜住。
5. **扩展靠接口**：新增采集源、新增平台只加类，不改编排。
6. **前端只做展示与交互**：所有权限、口径、状态机判断都在后端完成。

**依赖规则（必须遵守）**

1. `controller → service → mapper`，不跨层调用。
2. 跨业务域只允许调用对方的 service 接口，不直接引用其 mapper。
3. `common` 不得依赖任何业务包；`security` 只依赖 `user` 的只读能力。
4. 实体（entity）只在服务端流转；对前端的输出统一用 VO。
5. 前台接口不返回逻辑删除字段、内部 ID 之外的运维字段。

## 4.5 关键设计决策

| 编号 | 决策 | 理由 | 代价 / 约束 |
|---|---|---|---|
| D-01 | 用数据库唯一索引 `uk_current(game_id, platform_id, is_current)` 表达“当前价唯一” | 靠 MySQL 的 NULL 允许多行特性，天然区分“1 条当前价 + N 条历史” | 写入顺序必须是先归档后插入（BR-03） |
| D-02 | 最低价口径写成一段 SQL 片段，两处引用 | 避免“列表和详情算出两个最低价”这类事故 | 改口径必须同步改两处并回归 |
| D-03 | 逻辑删除 + 唯一索引组合时提供“复活”分支 | 删除后重建同编码平台不撞 `uk_code_region`，历史价不丢 | `restore` 必须手写 SQL（`updateById` 会被逻辑删除条件挡住） |
| D-04 | 采集采用策略模式 + 注册表 | 新增平台只加一个 `PriceSource` 实现 | 注册表按 `@Order` 取第一个可用源，顺序即优先级 |
| D-05 | 采集价偏离 > 50% 不覆盖，进待确认 | 抓取异常（币种错、页面改版）不应污染线上价格 | 需要人工审批，队列目前无通知 |
| D-06 | 汇率随价格固化（`rate`、`rate_time`、`cny_amount`） | 历史价不能被今天的汇率改写，保证走势可比 | 汇率不自动刷新时，新价格会沿用旧快照 |
| D-07 | JWT 自证 + Redis 黑名单 | 无状态扩展性好，同时支持“登出立即失效” | 黑名单 TTL 必须等于 token 剩余时间 |
| D-08 | 审计写库放在旁路 try/catch | 留痕失败不能阻断业务 | 审计异常只能从日志发现 |
| D-09 | 第三方官方史低独立成表 | 来源不同、口径不同，混入最低价会失真 | 前台需同时展示两套“史低”，易混淆，靠文案区分 |
| D-10 | 详情页为“已上架但无价”的平台生成占位卡 | 用户能看到“这个平台也卖”，只是暂时没价 | “能否展示”与“能否计入最低价”用两个字段分别控制（`listed` vs `api_ready`） |
| D-11 | 分页上限由 `PaginationInnerInterceptor` 兜底 200 | 防止 `size=99999` 拖垮数据库 | 业务层另有 `@Max(50)` 等更严限制 |

## 4.6 核心链路

### 4.6.1 列表查询（FR-01/02）

```
Vue GameList.vue
  ├ buildParams(): page,size,keyword,typeIds,platformIds,priceMin,priceMax,discountOnly
  └ GET /api/games
      └ GameController.list → GameServiceImpl.listGames
           ├ prepareKeyword: 去空格、小写；命中类型名则转成 typeIds
           ├ GameMapper.selectAppPage(IPage)  → 1 条分页 SQL（含 minPriceExpr）
           ├ loadCurrentPrices(gameIds)       → 1 条批量取当前价（platform 标签）
           └ loadTypeNames(typeIds)           → 1 条批量取类型名
      └ PageResult<GameListItemVO>
```

### 4.6.2 详情查询（FR-03～07）

```
GET /api/games/{id}
  └ GameServiceImpl.getGameDetail
       ├ 查 game（status=1，否则 40401）
       ├ 批量：game_platform（listed）、platform（有效平台）、region_risk、historical_low、price_record 聚合最低
       ├ 逐平台组装 PlatformPriceVO（现价/原价/折扣/汇率/史低/链接/风险）
       ├ 未关联但已上架的平台 → 占位卡（hasPrice=false）
       └ GameDetailVO{ platforms[], minPriceCny, platformCount, lastUpdateTime }
```

### 4.6.3 采集写入（FR-15）

```
POST /api/admin/collect/run?platformId=9
  └ CollectServiceImpl.run
       ├ 门禁：sourceType≠3 / enabled=1 / apiReady=1
       ├ 生成批次号 → 先插 collect_task_log(status=0)
       ├ SourceRegistry.find(platform, scenario) → SteamPriceSource
       ├ fetch()：补齐缺失 appid → 逐条拉价 → CollectItem 列表
       ├ 逐条 CollectPriceWriter.write（独立事务）
       │    ├ 校验金额/币种/折扣 → 汇率快照 → 读当前价
       │    ├ 同价：当天已有点则 skip(0)，否则继续写
       │    ├ 波动>50%：status=2 入待确认(2)
       │    └ 正常：归档旧 is_current → 插新行(1)
       └ finally：回写日志总数/成功/失败/状态
```

### 4.6.4 提醒判定（FR-11/12）

```
AlertCheckJob（每 60s）
  └ 取启用规则（status=1）
       ├ 取规则涉及游戏的当前价（统一口径，按 platform_id 过滤）
       ├ 按 type 比较：1 目标价 / 2 跌至官方史低 / 3 任意降价
       ├ 去重：与 last_fired_price 相同则跳过；价格回升不重复
       └ 触发：写 notification + 更新 last_fired_price/time
```

## 4.7 定时任务

| 任务 | 类 | 触发 | 说明 |
|---|---|---|---|
| 全量采集 | `job.CollectJob` | `0 0 4 * * ?` | 遍历所有 `enabled=1 AND api_ready=1` 的平台，单平台失败隔离 |
| 提醒判定 | `job.AlertCheckJob` | 固定间隔 60000 ms | 规则数量上限 500 条/轮 |

> 两者共用 Spring 默认单线程调度器，长任务会互相挤占；生产建议配置 `spring.task.scheduling.pool.size`（见第 10 章）。

## 4.8 统一响应与异常

**成功响应**

```json
{ "code": 0, "message": "成功", "data": { ... } }
```

**失败响应**

```json
{ "code": 40901, "message": "该游戏已存在", "errors": { "name": "该游戏已存在" } }
```

- `errors` 为字段级错误，仅参数校验与业务字段冲突时出现；`@JsonInclude(NON_NULL)` 保证空字段不输出。
- 全局异常处理器把 Spring 校验异常、参数绑定异常、`BizException`、未捕获异常统一映射为 `Result`。
- 未映射的媒体类型错误（如请求体缺少 `Content-Type`）会落到兜底分支返回 `50000`、HTTP 500，这是已知瑕疵。

## 5.2 实体关系

```
game_type ──1:N── game ──1:N── game_platform ──N:1── platform
   │                │                                  │
   │                ├──1:N── price_record ──────────────┤（逻辑关联）
   │                ├──1:N── historical_low ────────────┤
   │                ├──1:N── favorite（+ user_id）
   │                ├──1:N── alert_rule（+ user_id）
   │                └──1:N── notification（+ user_id / alert_rule_id）
   │
platform ──1:N── region_risk（platform_id + region）
platform ──1:N── collect_task_log
platform ──1:N── exchange_rate_snapshot（按 base_currency，与平台无直接关联）
sys_user ──1:N── favorite / alert_rule / notification / admin_audit_log(operator_id)

派生视图：v_game_min_price(game_id, min_price_cny, platform_count)
```

**关系要点**

- `price_record` 是核心事实表，`game_id + platform_id` 为逻辑主键组合；当前价唯一性由 `uk_current` 保证。
- `game_platform` 是“某游戏在某平台是否上架、外部 ID 是什么、跳转链接是什么”的唯一来源，采集器依赖它定位商品。
- `historical_low` 与 `price_record` **互不参与**：前者只展示官方史低，后者参与最低价与真实史低。

索引与约束：

```sql

KEY idx_gp_time (game_id, platform_id, recorded_at)
KEY idx_status (status)
KEY idx_current_platform (is_current, platform_id)
```

**关键设计：`uk_current` 为什么能工作**

MySQL 的唯一索引把 `NULL` 视为互不相等，因此：

| 行 | game_id | platform_id | is_current | 是否冲突 |
|---|---|---|---|---|
| A（当前价） | 1 | 9 | 1 | 占位 |
| B（历史点） | 1 | 9 | NULL | 不冲突（可无限多行） |
| C（历史点） | 1 | 9 | NULL | 不冲突 |
| D（第二条当前价） | 1 | 9 | 1 | **冲突** → 数据库层面挡住 |

这也决定了写入顺序：更新当前价时先把旧行 `is_current` 置 NULL，再插入新的 `is_current=1`。

**行类型对照**

| 场景 | is_current | status | 是否计入最低价 | 是否进入走势 |
|---|---|---|---|---|
| 正常当前价 | 1 | 1 | 是 | 是 |
| 历史采样 | NULL | 1 | 否 | 是 |
| 待确认（异常波动） | NULL | 2 | 否 | 否 |
| 已驳回 | NULL | 3 | 否 | 否 |

## 5.5 视图 v_game_min_price

```sql
CREATE OR REPLACE VIEW v_game_min_price AS
SELECT p.game_id,
       MIN(p.cny_amount)             AS min_price_cny,
       COUNT(DISTINCT p.platform_id) AS platform_count
FROM price_record p
JOIN platform pf ON pf.id = p.platform_id AND pf.enabled = 1
WHERE p.is_current = 1 AND p.status = 1
GROUP BY p.game_id;
```

- 用途：给运维/报表一个现成的“最低价”口径，避免手写 SQL 时漏条件。
- 注意：视图条件与 `minPriceExpr` **不完全等价** —— 视图没有 `api_ready=1 AND deleted=0`，而主查询有。因此**业务代码一律不用视图**，视图仅供人工排查。这一点必须在交接时说明，否则会出现“报表算出的最低价与页面不一致”的误判。

## 5.8 容量规划

单条价格记录按 150 B 估算（含变长字段与 NULL 位图），加索引约 250 B：

| 规模 | 行数/年 | 数据+索引 |
|---|---|---|
| 1,000 游戏 × 6 平台 × 1 点/天 | 2,190,000 | ≈ 550 MB/年 |
| 3,000 游戏 × 8 平台 × 1 点/天 | 8,760,000 | ≈ 2.2 GB/年 |

**应对策略（按优先级）**

1. 一年内无需处理（当前 20 行）。
2. 超过 200 万行后：`price_record` 按 `recorded_at` 做年度归档表（`price_record_2026`），主表只保留近 24 个月。
3. 归档后走势查询需回退到归档表（可在 `PriceTrendServiceImpl` 加一层“主表 + 归档表 UNION”）。
4. 不建议按 `game_id` 分区：查询模式是“按游戏取全部历史”，分区收益有限且增加维护成本。

| 拦截器 | 路径 |
|---|---|
| 普通（登录即可） | `/favorites/**`、`/alerts/**`、`/notifications/**`、`/auth/me`、`/auth/logout` |
| 管理员（`requireAdmin=true`） | `/admin/**` |

## 6.3 安全与认证（security 5 + user 9）

| 类 | 职责 | 关键点 |
|---|---|---|
| `JwtUtil` | 签发/解析 HS256 token | claims：`sub=userId`、`username`、`role`、`jti`；`expire-minutes` 读配置 |
| `AuthInterceptor` | 请求级鉴权 | `preHandle` 解析 Bearer → 校验黑名单 → 查用户状态 → 写 `UserContext`；`afterCompletion` 必须 `clear()` |
| `UserContext` | 线程级当前用户 | `ThreadLocal<LoginUser>`；`require()` 未登录抛 40100；`requireUserId()` 供服务层取当前用户 |
| `LoginUser` | 当前用户快照 | `userId` / `username` / `role` |
| `TokenInfo` | 解析结果 | `userId` / `username` / `role` / `jti` / `expireAt` |
| `AuthController` | 4 个端点 | register / login / logout / me |
| `AuthServiceImpl` | 认证业务 | 注册查重、BCrypt 加密、登录失败计数与锁定、签发 token、登出写黑名单、`me` 查询 |
| `SysUser` / `SysUserMapper` | 用户实体与 mapper | `@TableLogic deleted` |
| `LoginVO` / `UserVO` | 输出模型 | `LoginVO{token, user}`；`UserVO` 不含密码字段 |
| `RegisterRequest` / `LoginRequest` | 入参模型 | 用户名长度、密码强度、昵称长度由注解约束 |

**登录流程**

```
POST /auth/login
  → 查用户（不存在 → 40101，与密码错误同码，避免枚举）
  → 校验 locked_until（未到 → 40302）
  → BCrypt.matches 失败 → failed_count+1，达 5 次写 locked_until=now+15min → 40101
  → 成功 → failed_count=0、locked_until=null、写 last_login_time
  → 签发 token（jti 随机 UUID）→ LoginVO
```

**登出流程**

```
POST /auth/logout（需有效 token）
  → 解析 token 取 jti 与剩余时间
  → Redis SETEX  blacklist:<jti>  剩余秒数
  → 后续携带同一 token 的请求 → 40103
```

**要点**

- 黑名单 TTL 必须等于 token 剩余有效期，否则会出现“token 已过期但黑名单还在”或“token 还有效但黑名单已过期”的错配。
- `afterCompletion` 里的 `UserContext.clear()` 是线程池复用的前提，漏掉会导致身份串号。
- 密码强度：BCrypt 强度 10；库里存 `$2a$10$...`。
- 注册只校验 `username` 唯一，不校验邮箱/手机（字段预留但未启用）。

### 6.4.1 列表查询（`listGames`）

```
1. 参数归一：page/size 兜底；keyword → prepareKeyword()
2. 分页查询：gameMapper.selectAppPage(page, q)
      SQL 片段顺序：status=1 → keyword → typeIds → platformIds(EXISTS) → 价格区间 → discountOnly → ORDER BY
3. 批量取价：loadCurrentPrices(gameIds) → 平台标签（按 cny_amount 升序，putIfAbsent 去重）
4. 批量取类型名：loadTypeNames(typeIds)
5. 组装 GameListItemVO：minPriceCny / maxDiscountRate / platforms / gameTypeName / coverUrl
```

**关键词处理（`prepareKeyword`）**

- 去首尾空格、转小写后作为 `keywordNorm`；
- 先按类型名匹配：若关键词命中某个 `game_type.name`，把对应 `typeIds` 放进 `keywordTypeIds`；
- 查询时 `keyword` 同时匹配 `game.name`、`game.name_en`、类型名（`LIKE`），实现“搜‘角色扮演’也能出 RPG 游戏”。

**筛选 SQL 要点**

| 条件 | 写法 | 原因 |
|---|---|---|
| 平台筛选 | `EXISTS (SELECT 1 FROM game_platform ...)` | 避免 JOIN 造成行膨胀 |
| 价格区间 | 用 `minPriceExpr` 作为标量子查询参与 `BETWEEN` | 与展示值同源，避免“筛 100 元以下却出现 120 元” |
| 仅看折扣 | `minPriceExpr` 对应记录的 `discount_rate > 0` | 同上 |
| 排序 | `sort_weight DESC, id DESC` | 运营可控 + 稳定分页 |

**列表字段来源**

| VO 字段 | 来源 |
|---|---|
| `minPriceCny` | `minPriceExpr` 子查询 |
| `maxDiscountRate` | 当前价集合里最大的 `discountRate` |
| `platforms[]` | `selectCurrentPrices` 批量结果（`PlatformTag{platformId,code,name}`），按价格升序 |
| `typeName` | `loadTypeNames` |
| `hasPrice` | 当前价集合是否非空 |

### 6.4.2 详情查询（`getGameDetail`）

```
1. 查 game（不存在或 status=0 → 40401）
2. 批量：game_platform（按 gameId）→ Map<platformId, link>
3. 批量：platform（enabled=1）→ Map<platformId, platform>
4. 批量：region_risk（按 platformId 集合）→ Map<platformId, risk>
5. 批量：historical_low（按 gameId）→ Map<platformId, officialLow>
6. 批量：price_record 聚合（按 gameId 取每个平台的最高/最低/最近）→ 真实史低
7. 逐平台组装 PlatformPriceVO
8. 对“listed=1 但无价格”的平台补占位卡
9. 汇总：`minPriceCny`（各平台人民币价最小）、`platformCount`、`lastUpdateTime`；每个平台行各自带 `lowest`（是否最低）与 `lowestEverCny/lowestEverAt`（该平台真实史低）
```

**`PlatformPriceVO` 关键字段**

| 字段 | 含义 | 为空时的前台表现 |
|---|---|---|
| `hasPrice` | 该平台是否有可用当前价 | false → 占位卡“暂无报价” |
| `cnyAmount` | 人民币现价 | — |
| `originalCny` | 人民币划线价 | 无折扣时等于现价 |
| `discountRate` | 折扣率 | 0 → 不显示折扣角标 |
| `discountEndTime` | 折扣截止 | 空 → 不显示倒计时 |
| `historyLowCny` | 官方史低（`historical_low`） | 空 → 不显示“官方史低” |
| `lowestEverCny` / `lowestEverAt` | 真实最低价与日期 | 空 → 不显示“史低 ¥x” |
| `shopUrl` | 跳转链接 | 空 → 按钮禁用并提示原因 |
| `riskLevel` / `riskReason` | 锁区风险 | 0 → “无锁区风险” |
| `rate` / `rateTime` | 汇率与时间 | 展示“按 x.xxxx 汇率折算（时间）” |

**占位卡规则（D-10）**

- 只对 `listed=1` **且** 平台 `enabled=1` 的平台生成；
- 占位卡带有 `externalId`/`storeUrl` 时可点跳转；
- 占位卡**永远不参与** `lowest` 标记与 `minPriceCny` 计算；
- 判断“能否展示”用 `listed + enabled`，判断“能否计入最低价”用 `api_ready`，两者不可混用。

**真实史低计算**

- 取该游戏所有 `status=1` 的价格点（不限 `is_current`）中 `cny_amount` 最小的一条，记录其 `recorded_at` 作为史低日期；
- 不使用 `historical_low`（那是第三方官方史低，口径不同）。

### 6.5.1 走势聚合（`getHistory`）

**返回结构**

```json
{
  "gameId": 1,
  "gameName": "赛博朋克 2077",
  "days": 90,
  "platforms": [
    {
      "platformId": 9, "platformCode": "STEAM", "platformName": "Steam", "currency": "CNY",
```

**规则**

| 规则 | 说明 |
|---|---|
| 取点条件 | `status=1`（不要求 `is_current=1`），保证历史点全部可见 |
| 时间窗 | `days` 归一化到允许集合（30/90/180/365），默认 90 |

**前端配合（`PriceChart.vue`）**

- `seriesList` 由后端 `platforms[]` 映射为 ECharts 多 `series`（每个平台一条，`x=recordedAt`、`y=cnyAmount`）；
- `allInsufficient` 为真时展示“数据不足，暂无法生成趋势”；
- 史低参考线（`markLine`）只在 `史低 ≤ 最小点值` 时绘制，否则会画出“漂浮在图上方的线”。

### 6.5.2 手工录入（`createManualPrice`）

与采集写入共享同一套约束：

1. 金额 > 0、币种必须等于平台币种、折扣率与原价一致；
2. 汇率必须存在（缺失抛 `EXCHANGE_RATE_UNAVAILABLE`）；
3. 先归档旧 `is_current`，再插入新行；
4. `source_type=1`、`operator=管理员用户名`（当前硬编码为 `"admin"`，见 DEF-03）；
5. 写审计 `MANUAL_CREATE_PRICE`。

### 6.5.3 待确认审批（`PriceReviewService`）

```
GET  /admin/prices/pending        → 分页列出 status=2（含当前价对比、偏离比例）
POST /admin/prices/{id}/approve   → 校验仍为 status=2（否则 40905）
                                    → 归档该平台当前价 → 该行 is_current=1,status=1,verified_*
                                    → 审计 APPROVE_PENDING_PRICE
POST /admin/prices/{id}/reject    → status=3,verified_*，reason 存 source_ref 备注
                                    → 审计 REJECT_PENDING_PRICE
```

> 审批通过后**不会**自动触发提醒判定；下一次 60s 轮询才会通知用户。

|---|---|
| 门禁 | `data_source_type=3` → 40903；`enabled=0` → 40000；`api_ready=0` → 40903 |
| 批次号 | `{CODE}-{REGION}-{yyyyMMddHHmmss}-{4位随机}`，同时写入日志 `batch_no` |
| 先落日志 | `status=0`（运行中），保证进程崩溃也留痕 |
| 取采集器 | `SourceRegistry.find`；为空 → 日志 `status=3` + 抛出可读原因 |
| 逐条写入 | 每条 independent 事务；异常只累加 `fail`，继续下一条 |
| 状态判定 | `total=0` → 3；`fail=0` → 1；否则 2；整批异常 → 3 |
| finally | 回写 `end_time / total / success / fail / status / error_msg` |

**`write` 返回值语义**

| 返回 | 含义 | 计入 success |
|---|---|---|
| 1 | 写入当前价 | 是 |
| 0 | 跳过（同价且当天已有点 / 同价待确认已存在） | 否 |
| 2 | 进入待确认队列 | 否（`queue` 单独计数，日志里并入 success 之外的统计） |
| 抛出异常 | 该条失败 | 否（计入 fail） |

### 6.10.4 写入（`CollectPriceWriter.write`）

```
① 校验：金额>0；币种==平台币种；有折扣率则必须有原价且原价≥现价；
        折扣截止时间不得早于当前时间
② 汇率：getRateToCny(platform.currency) → rate/rateTime；缺失抛 EXCHANGE_RATE_UNAVAILABLE
③ 读当前价：selectOne(game_id, platform_id, is_current=1)
④ 同价分支（BR-09）：
     若 cny 与当前价相同
       → 查该 game+platform 当天 status=1 采样点数
       → >0：return 0（今天已有数据，避免重复点）
       → =0：打日志后继续写入（保证跨天必有 1 个点）
⑤ 组记录：currency/original_amount/original_price/discount_rate/rate/rate_time/
          cny_amount/source_type=采集器类型/source_ref=批次号/operator=collect:批次号
⑥ 波动判定：|新价-旧价| / 旧价 > 0.5 → 入待确认
       → 同价待确认已存在则 return 0，否则 insert(status=2, is_current=NULL) → return 2
⑦ 正常写入：update 旧行 is_current=NULL → insert 新行(is_current=1, status=1) → return 1
```

**为什么每条一个事务**：一条脏数据（币种错、原价倒挂）不能回滚整批，否则“采集一次全失败”。

## 6.13 定时任务 job（2 个类）

| 任务 | 类 | 触发 | 逻辑 |
|---|---|---|---|
| 全量采集 | `CollectJob` | `cron = 0 0 4 * * ?` | 调用 `CollectService.runAll("NORMAL")`，逐平台执行，单平台异常不影响后续 |
| 提醒判定 | `AlertCheckJob` | `fixedDelay = app.alert.check-interval-ms`（60s） | 取启用规则 → 批量取价 → 按类型比较 → 去重 → 写通知 |

**`AlertCheckJob.evaluate` 判定细节**

| type | 触发条件 | 依赖 |
|---|---|---|
| 1 目标价 | 当前最低价 ≤ `target_price` | 实时价 |
| 2 跌至史低 | 当前最低价 ≤ 官方史低（`historical_low.low_cny`） | 官方史低存在 |
| 3 任意降价 | 当前最低价 < `baseline_price` | 实时价 |

**去重锚点 `last_fired_price`**

- 与上次触发价相同 → 跳过（同价不重复轰炸）；
- 价格回升后再降到同一价位 → 仍跳过（只有创出更低价才再通知）；
- 首次触发后写 `last_fired_price` / `last_fired_time`。

**上限**：每轮最多处理 500 条规则，超出部分下轮处理（当前仅 1 条规则，无影响）。

# 7 安全设计

## 7.1 认证

| 项 | 实现 |
|---|---|
| 令牌类型 | JWT（HS256），无状态 |
| 载荷 | `sub`（userId）、`username`、`role`、`jti`、`iat`、`exp` |
| 有效期 | 120 分钟（`app.jwt.expire-minutes`） |
| 传输 | `Authorization: Bearer <token>`，前端存 `localStorage.gp_token` |
| 主动失效 | 登出时把 `jti` 写入 Redis 黑名单，TTL = 剩余有效期 |
| 校验顺序 | 取头 → 解析 → 黑名单 → 用户存在且 `status=1` → 角色判断 |

## 7.2 授权

| 范围 | 规则 | 实现 |
|---|---|---|
| 公开 | 无 token 可访问 | `/games*`、`/game-types`、`/platforms`、`/auth/login`、`/auth/register` |
| 登录 | 需有效 token | `/favorites/**`、`/alerts/**`、`/notifications/**`、`/auth/me`、`/auth/logout` |
| 管理员 | token + `role=2` | `/admin/**` |
| 数据隔离 | 服务层强制按当前用户过滤 | 收藏、提醒、通知 |

**越权防护点**

- 收藏/提醒/通知的所有读写都带 `user_id = UserContext.requireUserId()`；
- 提醒的启停/删除调用 `requireOwn`，非本人 403；
- 后台接口不依赖前端隐藏菜单，拦截器独立判定。

## 7.3 密码与防爆破

| 项 | 值 |
|---|---|
| 算法 | BCrypt（强度 10） |
| 存储 | `password_hash`，永不返回前端 |
| 失败锁定 | 连续 5 次 → 锁定 15 分钟（`locked_until`） |
| 错误提示 | “用户不存在”与“密码错误”统一返回 40101，避免账号枚举 |
| 重置 | 本期无找回密码功能 |

## 7.4 输入与数据安全

| 风险 | 现状 | 建议 |
|---|---|---|
| SQL 注入 | MyBatis-Plus 参数绑定 + XML 使用 `#{}` | 保持，禁止 `\${}` 拼关键字 |
| XSS | 前端 Element Plus 文本渲染默认转义；无 `v-html` 使用 | 保持 |
| 全表误删 | `BlockAttackInnerInterceptor` 拦截无 where 的 update/delete | 保持 |
| 分页拖库 | `maxLimit=200` + 接口级 `@Max(50)` | 保持 |
| 链接注入 | 模板只校验含 `{externalId}`，未校验协议 | 加 `https://` 前缀校验（T-04） |
| 敏感配置 | `application.yml` 明文写库密码与 JWT secret | 生产改环境变量/配置中心（T-05） |

## 7.5 审计

- 覆盖：游戏增改上下架、平台增改启停删除复活、链接保存、手工价格、待确认审批。
- 不留痕：收藏、提醒、通知等用户侧操作（无审计价值）。
- 缺陷：审计只写不读（无查询接口/页面），`LINK_UPDATE` 只记录 `storeUrl`。

## 8.9 常见故障排查

| 现象 | 可能原因 | 处理 |
|---|---|---|
| 后端启动即退出，日志无内容 | 未设 `JAVA_HOME` | 先设环境变量再执行 `start.ps1` |
| `mvn spring-boot:run` 报路径错误 | 中文目录 | 改为 `package` 后 `java -jar` |
| 接口 500，日志报 `Communications link failure` | MySQL 未启动 / `localhost` 解析问题 | 确认服务启动，连接串用 `127.0.0.1` |
| 登录一直 40102 | token 过期 / 本机时间偏差 | 重新登录；校准系统时间 |
| 登出后原 token 仍可用 | Redis 未启动，黑名单写入失败 | 启动 Redis，检查连接配置 |
| 列表价格为空 | 平台 `api_ready=0` 或 `enabled=0` | 后台检查平台三重状态 |
| 采集 `total=0` | Epic 无 `external_id` / 网络或证书问题 | 补外部 ID；查 `collect_task_log.error_msg` |
| 采集显示成功但价格没变 | 同日去重（BR-09） | 属正常；看日志 `success=0 skip>0` |
| 详情页史低为空 | 该游戏没有历史点（新游戏） | 先采集出至少 1 个点 |
| 后台 403 | 当前账号 role≠2 | 使用管理员账号或插入管理员 |
| 前端 401 后一直跳登录 | localStorage 残留旧 token | 清理 `gp_token` 后重登 |

## 10.2 技术债

| ID | 技术债 | 影响 | 处理建议 |
|---|---|---|---|
| T-01 | 采集无分布式锁 | 并发写入同一 `game+platform` 时可能一条失败 | Redis `SETNX` 按平台加锁，或 `collect` 串行队列 |
| T-02 | `run-all` 串行且每条 `sleep 200/300ms` | 平台多时单次采集耗时长 | 改线程池（每平台一任务，限并发 3） |
| T-03 | 调度器默认单线程 | 采集与提醒判定互相阻塞 | 配 `spring.task.scheduling.pool.size=4` |
| T-04 | `linkTemplate` 只校验占位符，不校验协议 | 可存入 `javascript:` 等危险链接 | 增加 `https://` 前缀校验 + 后台预览 |
| T-05 | 库密码、JWT secret 明文写在 yml | 泄露风险 | 改环境变量 / 配置中心 |
| T-06 | `AdminPlatformService.listAll` 每平台 2 次 `selectCount`（N+1） | 平台增多后后台变慢 | 改 1 条聚合 SQL（`GROUP BY platform_id`） |
| T-07 | 走势查询无点数上限 | 极端参数可拉全量历史 | 加 `limit` 或按天聚合（超过 180 天按周取点） |
| T-08 | 生产仍开 `StdOutImpl` SQL 日志与 debug 级别 | 日志膨胀、性能损耗 | 生产 profile 覆盖为 `info` + 关闭 SQL 打印 |
| T-09 | `schema.sql` 无种子数据 | 新环境空库，无法自测 | 补 `seed.sql`（类型、平台、管理员） |
| T-10 | 审计 `before/after` 直接序列化实体/Map | 字段改名会导致历史审计难以解读 | 定义审计 DTO，只记关键字段 |
| T-11 | `v_game_min_price` 与业务口径不一致（缺 `api_ready`/`deleted`） | 人工用视图核对会得出不同结果 | 统一视图条件，或在注释中明确“仅排查用” |
| T-12 | 详情页 5 条批量查询在游戏无平台时仍执行 | 轻微浪费 | 空集合短路 |

# 12 Epic 浏览器渲染采集（增量，2026-11-27）

## 12.1 背景与结论

Steam 采集走官方 `appdetails` 接口即可，Epic 不行：

| 通道 | 结果 |
|---|---|
| `store.epicgames.com/graphql`（searchStore） | HTTP 403（Cloudflare 挑战页） |
| `launcher.store.epicgames.com/graphql` | HTTP 500 / 403 |
| `curl.exe` 直连商品页 | HTTP 403（换 TLS 指纹无效） |
| `msedge --headless=new --dump-dom` | 返回挑战页（标题“请稍候…”） |
| **真实浏览器窗口（非无头，窗口置于屏幕外）** | **正常渲染，标题“《赛博朋克 2077》 | Epic游戏商城”，可读到 ¥298.00** |

结论：Epic 只能用“本机浏览器 + DevTools 协议（CDP）”渲染后读 DOM，即 `EdgeCdpClient` + `EpicBrowserPriceSource`。

## 12.2 模块设计

| 文件 | 职责 | 关键位置 |
|---|---|---|
| `collect/source/browser/EdgeCdpClient.java` | 拉起本机浏览器、建立 CDP WebSocket、执行取值表达式 | `render()`:89、`start()`:178、`detectBrowser()`:223、`shutdown()`（`@PreDestroy`） |
| `collect/source/EpicBrowserPriceSource.java` | Epic 采集器：读链接→推导 slug→开页→解析价格 | `EXTRACT_JS`:55、`fetch()`:78、`resolveSlug()`:112、`parse()`:134 |

设计要点：

1. **单实例常驻**：浏览器进程首次启动约 4~6 秒，之后每页 2~4 秒；`ensureReady()` 复用同一进程。
2. **窗口离屏**：`--window-position=-32000,-32000`，不打扰用户；`user-data-dir` 持久化，Cloudflare 的 `cf_clearance` cookie 可复用。
3. **取值靠轮询 Promise**：`render()` 下发 `Runtime.evaluate`（`awaitPromise:true`），内部 JS 每 700ms 试一次，命中或超时（默认 20s）才返回，因此不依赖固定 `sleep`。
4. **只取“购买卡片”**：容器过滤条件为 `长度 20~600 && 含 ¥金额 && 含“购买”`。必须要求含金额——实测仅按“购买”过滤会命中 4 个字符的导航节点，导致取不到价（已踩坑并修正）。
5. **折扣只认 `-xx%`**：页面还有“返利 5%”这类文案，早期正则会误取成折扣率（GTA V 曾写成 5%），已收紧为 `/-\s*(\d{1,2})\s*%/`。

## 12.3 配置项（`application.yml` 69~76 行）

```yaml
      epic-browser-enabled: true      # false 时回落到 GraphQL 版 EpicPriceSource
      epic-browser-locale: zh-CN      # 决定页面语言与币种（zh-CN → CNY）
      browser:
        browser-path: ""              # 空 = 自动探测 Edge / Chrome
        port: 9333
        profile-dir: ""               # 空 = 用户目录\.gameprice-browser
        timeout-ms: 20000             # 单页等待上限
```

自动探测顺序：`Program Files (x86)\Microsoft\Edge\...` → `Program Files\Microsoft\Edge\...` → Chrome 三个常见路径 → `%LOCALAPPDATA%\Google\Chrome\...`。

## 12.4 运行流程

```
CollectService.run(platform=10)
  → SourceRegistry.find() 选中 EpicBrowserPriceSource（@Order(1)，先于 GraphQL 版）
  → fetch(): 取 game_platform(listed=1)
      → resolveSlug(): external_id 优先，缺失则从 store_url 的 /p/{slug} 推导
      → EdgeCdpClient.render("https://store.epicgames.com/zh-CN/p/{slug}")
          → ensureReady() → /json/list 取 page 目标 → WS 连接 → Page.navigate
          → Runtime.evaluate(EXTRACT_JS, awaitPromise) → 返回 {amounts, discount}
      → parse(): 第 1 个金额=现价，更大者=原价，折扣率兜底反算
      → sleep(500) 节流
  → CollectPriceWriter.write()（同日去重、剧烈波动进待确认，规则不变）
```

## 12.6 运维与排障

1. **停止**：`.\stop.ps1` 已扩展为同时结束带 `gameprice-browser` 目录或 `remote-debugging-port=9333` 的浏览器进程；后端正常关闭时也会走 `@PreDestroy` 收掉子进程。
2. **采集周期**：每日 04:00 `collect.cron` 全量采集会包含 Epic；单轮耗时约等于“浏览器冷启动 + 每款 2~4 秒”。
3. **排障顺序**：
   - 日志出现“未找到 Edge/Chrome” → 配置 `browser-path`；
   - 日志出现“页面未取到内容” → 先手工 `msedge --remote-debugging-port=9333` 打开同 URL 看是否被拦；
   - 取到内容但无价格 → 只改 `EpicBrowserPriceSource.java:55` 的 `EXTRACT_JS`；
   - 价签对不上（折扣/原价）→ 检查 `parse()` 的金额配对规则。

## 12.7 已知限制

1. Epic 改版（DOM 结构变化）会导致取不到价，唯一修法是调 `EXTRACT_JS`，属于长期维护点。
2. 只在 Windows 本机可用（依赖本机浏览器与离屏窗口）；服务器无桌面的环境需改用 Playwright/容器方案。
3. `external_id` 必须是 Epic `productSlug`；新加游戏时若 `store_url` 可解析则自动推导，否则采集会跳过并记日志。
4. 采集本质是“读公开商店页”，保持每天一次的频率，不做高频轮询。

## 13.2 游戏信息校验与补齐（中文名 / 英文名 / 发行日期）

### 13.2.1 表结构调整

```sql
ALTER TABLE game ADD COLUMN release_date DATE NULL COMMENT '精确发行日期（Steam 校验补齐）' AFTER release_year;
```

- `release_year`（smallint）保留，用于列表筛选/排序；
- `release_date`（date）为新字段，精确到日，缺失时为 NULL；
- 实体 `Game` 新增 `private java.time.LocalDate releaseDate;`（紧跟 `releaseYear` 之后）。

### 13.2.2 数据来源与判定规则

数据源：Steam 官方 `appdetails`，两个语言各取一次

| 用途 | 请求 |
|---|---|
| 中文名 + 中文日期 | `?appids={id}&l=schinese&cc=cn` |
| 英文名 + 英文日期 | `?appids={id}&l=english&cc=us` |

处理规则（顺序执行）：

1. **空字段直接补**：中文名为空、英文名为空、`release_date` 为空、`release_year` 为空 → 用 Steam 值写入；
2. **已有值不一致只报告、不覆盖**：返回 `MISMATCH`，弹窗里列出「库里值 / Steam 值」；需要改写时用 `force=true`（前端弹窗勾选「强制覆盖」）；
3. **名称归一化比较**：去掉空白（含全角）、`《》「」()（）:：-—/·,.'’‘"`、`™®©`、转小写；**一方包含另一方即算一致**，所以 `Sekiro: Shadows Die Twice` ↔ `Sekiro™: Shadows Die Twice - GOTY Edition` 不误报；
4. **年份对齐**：补 `release_date` 后，若 `release_year` 为空则同步回填为日期年份；
5. 每次写入都落 `admin_audit_log`（`module=GAME, action=META_UPDATE`），`before/after` 含 name/nameEn/releaseYear/releaseDate。

状态码：`OK`（一致）/ `FILLED`（已补齐）/ `MISMATCH`（不一致未覆盖）/ `NO_STEAM`（无 Steam 链接）/ `ERROR`（Steam 接口无数据）。

### 13.2.3 采集链路内嵌

- `CollectServiceImpl` 注入 `GameMetaService`，开关 `app.collect.meta-sync: true`；
- 采集循环收集本轮所有 `gameId`（**同价跳过的也收**，否则日常全跳过时就永远不会补全）；
- 每批采集结束后异步执行 `syncMissing(ids)`：只有「英文名空 / release_date 空 / release_year 空」的才会真正请求 Steam，字段齐全的直接跳过，日常几乎无额外开销；
- 失败只打 debug 日志，绝不影响价格入库。

### 13.2.4 实测（2026-11-27）

- 全库 22 款，`POST /admin/games/meta/backfill?force=false` 耗时 **19.3s**：18 款一致/已补齐，4 款 `MISMATCH`；
- 补齐样例：赛博朋克2077 `2020-12-09`、艾尔登法环 `2022-02-24`、双人成行 `2021-03-25`、GTA V 增强版 `2025-03-04`；
- 4 条 MISMATCH 全部是「Steam 中文接口返回英文名」：只狼 `Sekiro™: Shadows Die Twice - GOTY Edition`、文明六 `Sid Meier's Civilization® VI`、怪物猎人：世界 `Monster Hunter: World`、怪物猎人：崛起 `MONSTER HUNTER RISE` —— 保留库里中文名即可，**不需要处理**；
- 采集内嵌验证：手工把 GTA V 的 `release_date` 置空 → 跑一次 STEAM-CN 采集（22 条全同日同价跳过）→ 15s 后 `release_date` 自动回填 `2025-03-04`，审计日志出现 `META_UPDATE game=13 steamAppId=3240220`（id 209）。

## 13.3 Epic 链接补齐（批量 + 导入自动挂）

### 13.3.1 难点

Epic 商品标题是**本地化中文名**，与 Steam 名称经常不同：`HITMAN World of Assassination` ↔ Epic《HITMAN暗杀世界》；`Control Ultimate Edition` ↔ Epic《控制 终极版》。因此不能只按 URL 猜，必须搜店 + 名称匹配。

### 13.3.2 实现

- 搜索页：`https://store.epicgames.com/{locale}/browse?q={关键词}&sortBy=relevancy`（`/search?q=` 会 302 到 www.epicgames.com，禁用）；
- 用 Edge+CDP 渲染后执行 `SEARCH_JS`：取 `a[href^="/p/"]` 的 slug 与标题，过滤含 `--` 的终极版/DLC，最多 8 条；
- 三档匹配：归一化完全同名 → 英文名同名 → 标题以游戏名开头且长度差 ≤ 4；
- 中文名匹配失败时，**再用 `nameEn` 搜一次**（本轮新增兜底，提升一档命中）；
- 命中才插 `game_platform(EPIC)`，`store_url` 用平台 `link_template` 替换，写审计 `GAME/LINK_UPDATE`。

### 13.3.3 实测

| 场景 | 结果 |
|---|---|
| 全库补齐（第一版） | 22 款 / 51.6s：EXISTS 4、NOT_FOUND 18 |
| 全库补齐（加 nameEn 兜底后） | 23 款 / 116.3s：EXISTS 4、NOT_FOUND 19（含测试导入 1 款） |

- 已挂上：赛博朋克2077 `cyberpunk-2077`、文明六 `sid-meiers-civilization-vi`、双人成行 `it-takes-two`、GTA V 增强版 `grand-theft-auto-v`；
- NOT_FOUND 大头是**Epic 确实没有**（Capcom/育碧系基本不在 Epic 国区，怪物猎人：崛起抽查确认无货）；
- 少数是**译名不同导致漏匹配**：HITMAN `hitman-3`、Control。

### 13.3.4 已知限制与后续方案

1. 译名差异类漏匹配，目前只能人工在「链接」弹窗里填 slug；
2. 后续可二选一：**别名表**（Steam 名称 → Epic slug，命中优先查表，不误挂）或**候选确认弹窗**（列出候选人工点选）；
3. 浏览器逐款 3~5 秒，20 款约 1~2 分钟，前端超时已放到 300s。

## 13.4 小黑盒（Heybox）链接补齐

### 13.4.1 关键结论

小黑盒游戏详情页直接按 **Steam appId** 定位，无需搜索、无需匹配、无需浏览器：

```
https://www.xiaoheihe.cn/app/topic/game/pc/{steamAppId}
```

实测 `/pc/1091500` → 《赛博朋克2077》（¥89.4 / 史低 / -70%），`/pc/1245620` → 《艾尔登法环》，匿名可访问。

| 字段 | 原值 | 新值 |
|---|---|---|
| `link_template` | `https://api.xiaoheihe.cn/game/share_game_detail?appid={externalId}&game_type=pc` | `https://www.xiaoheihe.cn/app/topic/game/pc/{externalId}` |
| `data_source_type` | 3（无接口，禁止采集） | 2（浏览器渲染采集） |
| `api_ready` | 0 | 1 |
| `enabled` | 1 | 1 |

### 13.4.3 实现 `HeyboxLinkServiceImpl`

- `ensureLink(gameId)`：取 Steam appId → 拼 URL → 插 `game_platform(platform_id=11)` → 审计；
- **修复历史脏数据**：库里原有 6 条小黑盒链接 `external_id` / `store_url` 均为 NULL，检测到空值就按 Steam appId 重写（返回 `NEW` + 「已修复空的小黑盒链接」）；
- `backfillAll()`：遍历 `status=1` 游戏；
- 导入链路：`GameImportServiceImpl` 插完 Steam 链接后**同步**调 `ensureLink`（纯本地拼串，无网络开销）。

## 13.5 小黑盒价格采集（`HeyboxBrowserPriceSource`）

### 13.5.1 为什么还要浏览器

小黑盒没有对外价格接口（`api.xiaoheihe.cn` 需要签名/登录），但详情页对匿名用户公开，所以复用第 12 章的 `EdgeCdpClient` 渲染读价。

### 13.5.2 页面结构与取价规则

价格区 `div.price-row` 文本形如：

```
¥ 89.4 | 历史最低 剩余13天 | -70% | ¥298 | 领券9折 | 全区价格/趋势
```

| 字段 | 来源 |
|---|---|
| 原价 | `document.querySelector('.price-row p.original')` 里的 ¥ 金额（如 298） |
| 现价 | 价格行内金额中「不等于原价」的最小值（如 89.4） |
| 折扣 | 页面 `-NN%`；缺失时按 `(原价-现价)/原价` 计算 |
| 币种 | 平台结算币种（CNY） |
| 防串号 | `.game-name` 的「中文名 / 英文名」两行，逐行与 `game.name`、`game.name_en` 归一化比对 |

- 页面无价格（免费 / 未开售 / 限区）→ 返回 null，跳过不落库；
- 现价 ≤ 0 一律忽略，避免把「免费」写成 0 元；
- 款间隔 `heybox-interval-ms`（默认 400ms）温和节流。

### 13.5.3 开关与配置（`application.yml`，在 `meta-sync` 之后）

```yaml
heybox-enabled: true        # 关掉即不采小黑盒（链接补齐不受影响）
heybox-interval-ms: 400     # 每款之间停多久
```

### 13.5.4 实测（2026-11-27）

- 单平台 `POST /admin/collect/run?platformId=11&scenario=NORMAL`：**38.7s**，22 款全有价（成功 9 / 同日同价跳过 13 / 失败 0）；
- `POST /admin/collect/run-all`：**61.2s**，三个批次 platformId=9（22 条）、10（4 条）、11（22 条）—— 说明**小黑盒已进入自动采集**（`CollectJob` 每日 04:00 就是调 `runAll`）；
- 入库抽样：

|---|---|---|---|
| 赛博朋克2077 | ¥89.40 | ¥298 | -70% |
| GTA V 增强版 | ¥98.60 | ¥224 | -56% |
| 双人成行 | ¥39.60 | ¥198 | -80% |
| HITMAN World of Assassination | ¥95.20 | ¥238 | -60% |
| 艾尔登法环 | ¥298 | ¥298 | 0 |

### 13.5.5 踩坑记录（必读）

**坑 1：页面名只取第一行 → 10 款被判“名称不匹配”跳过。**
`.game-name` 是「中文名\n英文名」两行，第一版 JS 用 `split('\n')[0]`，于是：
- 库里 `Grand Theft Auto V 增强版` vs 页面「侠盗猎车手 V 增强版 / Grand Theft Auto V Enhanced」→ 对不上；
- 库里 `Hitman: Blood Money` vs 页面「杀手4：血钱 / Hitman: Blood Money」→ 对不上。

修法：JS 返回整段（换行转 `|`），Java 侧 `nameMatches()` 逐行比对中文名/英文名，任一行命中即通过；修复后跳过数 10 → 0。

**坑 2：`data_source_type=3` 会直接被采集入口拒掉（错误码 40903「该平台一期不支持」）。**
即使写好了采集器，平台仍是 3 也进不来，必须改成 2。

**坑 3：小黑盒价格是「黑盒价（含券后价）」**，与 Steam 区价口径不同（如赛博 `89.4` vs Steam 折扣价），两条折线有差异属正常，不是 bug。

## 13.8 运维提示

1. 小黑盒/Epic 采集都依赖本机浏览器（离屏窗口），`.\stop.ps1` 已含清理逻辑；
